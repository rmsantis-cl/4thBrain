# Bug 101: Actuator Sequence — Stuck Documents, No Instrumentation

**Stories:** 2.1 (Local LLM Metadata & Tag Inference), 3.1 (Smart Connections Vector Indexing Pipeline), 4.1 (Background Sweep & Queue Execution Script), 13.4 (Actuator Queue Monitoring Dashboard)

**Date Discovered:** 2026-09-02 (observed by user while testing Story 13.4's Actuators panel)

## Observed Behaviour

Documents get stuck in an actuator — for example, the Ingestor — and never progress further through the pipeline. Verified by the document/job remaining in a permanent `New` state — it never transitions to `Running`, `Completed`, or any subsequent actuator's state.

## Expected Behaviour

The actuator works without pause: it evaluates the routing rules, hands off immediately per `documets/design/Ingestion-State-Diagram.md`, messages the next actuator, and logs the in/out operation. A document should only ever be at rest while an actuator is actively working on it — never sitting idle waiting for something else to notice and move it forward.

The routing rules referenced are the ones already defined in `documets/design/Ingestion-State-Diagram.md` (the canonical Mermaid `stateDiagram-v2`), which specifies the actuator sequence and the branch conditions between them (e.g. text vs. binary at Ingest, index success/fail/too-short deciding whether Classify runs at all).

## Root Cause

No actuator ever enqueued the next stage's job. `ingest-executor.js`, `transcode-executor.js`, and `html-sanitize-executor.js` each finished their own work and left the document in `Processing`, but none of them called `job.create()` for the next stage. `vault/index-executor.js` didn't touch the database at all — it ran the watcher/status scripts and returned a result, but never wrote back a routing decision. `classification-executor.js` left the document in `Processing` forever instead of a terminal status. The pipeline's sequencing also didn't match the diagram: classify was gated directly off ingest/convert's output, with index disconnected from the branch (index success/fail/too-short) that the diagram says should decide whether classify even runs.

## Fix

- `ingest-executor.js` / `transcode-executor.js` / `html-sanitize-executor.js`: on success, enqueue an `index` job (`TextPath`/`BinaryExtract --> RAGIndexing`).
- `vault/index-executor.js`: gated `canHandle` on document existing + `Processing` + file present; `execute()` now branches per `RouteByResult` — too-short content sets the document `Archived` (`VAULT_NOTES`, terminal, no job) without spawning the watcher scripts; a watcher/status failure sets the document `Failed` (`VAULT_RAW`, terminal) and rethrows; success enqueues a `classify` job.
- `classification-executor.js`: final status changed from `Processing` to `Indexed` once the file is filed at its topic path (`Classify --> VAULT_TREE --> [*]`, terminal).
- `batch/worker.js`: `job_started`/`job_skipped`/`job_completed`/`job_failed` log lines now include `documentId`; `job_completed` already logs each executor's returned `result`, which now carries `sourcePath` (IN), `destPath` (OUT), and `next` (the actuator/terminal destination handed off to) — satisfying the Instrumentation Required section below for every actuator in the document-ingestion pipeline.
- `server/lib/repositories/job.js`: added `listByDocumentId` (used by the fix's own tests to verify a document's full job chain).

## Scope note: `batch/briefing-executor.js`

This file is listed below under Related Files as needing the same handoff/instrumentation treatment, but it was deliberately left out of this fix. `documets/design/Ingestion-State-Diagram.md` — the design artifact this bug's fix must implement — covers document ingestion only (EP1/EP2/EP3); the daily briefing pipeline (EP5, Story 5.1) is a separate, schedule-triggered synthesis job with no document handoff chain and no corresponding diagram, so there's no design artifact to implement instrumentation against here (per `.claude/rules/design-before-implementation.md`). If briefing-level instrumentation is wanted, it should be scoped under EP5/Story 5.1's own design rather than folded into this document-ingestion bug fix.

## Instrumentation Required to Verify the Solution

Every actuator must log, for each document it handles:
- The **IN document** it received (document id + path).
- The **OUT document** it produced (document id + path — may differ from IN, e.g. after conversion or a vault move).
- The **actuator the OUT document was sent to** next (or the terminal vault destination if this was the last stage).

This is the mechanism by which the fix is verified: if every actuator logs its in/out/handoff, a stuck document is visible directly in the log as "last successful handoff was to X, nothing since" — no separate tracing logic needed, and no document can go silently missing between stages.

## Status

**Fixed** — see `batch/worker.js`, the four ingestion-pipeline executors, and `vault/index-executor.js`. Verified by `batch/test/worker.test.js`'s "Bug 101: an ingested document is handed off through 'index' across consecutive sweeps, without external help" end-to-end test, plus per-executor handoff tests in `server/test/` and `vault/test/index-executor.test.js`. `batch/briefing-executor.js` intentionally excluded — see Scope note above.
