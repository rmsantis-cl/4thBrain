# Plan: Implement Story 2.1 (Local LLM Metadata & Tag Inference)

## Context

Story 2.1 bridges the ingestion pipeline (Story 1.1) and vault indexing (Story 3.1) by adding LLM-based classification. The pipeline today:

1. Story 1.1 ingests raw files → `$VAULT_DIR/incoming` + job record
2. Story 2.1 (this) classifies each → infers tags, topic/subtopic, generates YAML frontmatter, relocates attachments
3. Story 3.1 indexes the result → triggers Smart Connections embedding for the vault

**Dependencies:**
- **Story 1.1** (COMPLETED) — files already ingested and available in `$VAULT_DIR/incoming`
- **Story 7.1** (WIP/GPU spike done) — Ollama reachable at `http://localhost:11434` with `llama3.2:3b` loaded

**Design anchors:**
- ADR15 (topic/subtopic vault path, sibling attachments)
- ADR10 (concurrency=1 guard for Ollama calls)
- Story 1.1's `ingest` job_type executor pattern

## Architecture decisions (to confirm)

1. **LLM Prompt Strategy** — Use a few-shot prompt that:
   - Takes the raw note content as input
   - Outputs structured JSON: `{tags: [...], topic: "...", subtopic: "...", content_markdown: "..."}`
   - Preserves user-provided tags (prefixed or in a separate `user_tags` field)
   - Enforces topic/subtopic against vault taxonomy (from `params.json`)

2. **Attachment Relocation** — After classification:
   - Scan the note's Markdown for embedded image/document references (`![...](path)`, `[...](path)`)
   - Move referenced files from `$VAULT_DIR/incoming` to `$VAULT_DIR/{topic}/{subtopic}/.attachments/`
   - Rewrite the Markdown links to point to the new locations

3. **Frontmatter Generation** — Format:
   ```yaml
   ---
   title: {inferred or extracted from content}
   tags: {combined user + inferred}
   topic: {inferred}
   subtopic: {inferred}
   created: {timestamp}
   source: {original source: web-clip, file, email, etc.}
   ---
   ```

4. **Error Handling** — If LLM inference fails:
   - Mark job as `failed` (Job status enum)
   - Log reason (can't reach Ollama, invalid response, etc.)
   - Retry eligible per Story 4.1's job queue logic (TBD: max retries)

5. **Job Execution** — Follow Story 1.1's executor pattern:
   - New executor type: `job_type='classify'`
   - Input: `Document` record from ingestion (path, raw content, detected MIME type)
   - Output: Updated `Document` record with generated frontmatter + tags; `JobFile` record marking the relocation
   - Acquires ADR10 concurrency lock before calling Ollama

## Work breakdown

### Phase 1: Prompt & LLM Integration (1–2 hours)

1. **Design the classification prompt** — write a few-shot example that produces valid JSON output for a sample note
   - Test locally in Ollama's web chat to validate
   - Decide on taxonomy extraction (hardcode vault topics/subtopics from `params.json`? or ask LLM to map to closest match?)
   - Save the prompt template to `ingestor-classification/prompts/classify.md` for reference

2. **Create `ingestor-classification/lib/ollama-client.js`** — wrapper around `http://localhost:11434/v1/chat/completions`:
   - Accept `(content, prompt_template)` → returns parsed JSON `{tags, topic, subtopic, ...}`
   - Handle connection errors, timeouts, invalid JSON gracefully
   - Respect ADR10 concurrency gate (acquire lock before calling, release after)

### Phase 2: Classification Executor (2–3 hours)

3. **Create `ingestor-classification/lib/executors/classify-executor.js`**:
   - Implement `canHandle(job)` — true if `job.job_type === 'classify'`
   - Implement `execute(job, db)`:
     - Load the `Document` and `JobFile` records
     - Read raw content from disk (at the path stored in `JobFile.file_path`)
     - Call Ollama classification (Phase 1's client)
     - Parse response → extract tags, topic, subtopic
     - Generate YAML frontmatter
     - Write the classified note to disk (target path determined by topic/subtopic per ADR15)
     - Relocate referenced attachments
     - Update `Document` record: set `status='Classified'`, add tags via `document_tag` junction
     - Create `JobFile` records for each relocated attachment
     - Mark job as completed (`job.status='Completed'`)

4. **Register executor in `batch/job-executors.js`**:
   - Add `'classify': ClassifyExecutor` to the dispatch table

### Phase 3: Job Queue Integration (1 hour)

5. **Wire classification into the job queue**:
   - After Story 1.1's ingestion creates a `job_type='ingest'` record, it already creates the `Document` + `JobFile` records
   - Add a second job record: `job_type='classify'` with `depends_on=ingest_job_id` (if we add dependency support to the queue, else rely on sequencing)
   - Alternatively: Story 1.1's executor itself enqueues a `'classify'` job after ingestion succeeds

6. **Update `batch/worker.js`** if needed:
   - Ensure it calls `ClassifyExecutor.execute()` for classify jobs
   - No changes expected — should just work via the dispatch table

### Phase 4: Testing (2–3 hours)

7. **End-to-end test** (`ingestor-classification/test/classify-executor.test.js`):
   - Mock Ollama responses (structured JSON)
   - Test classify executor:
     - Reads test file from `$VAULT_DIR/incoming`
     - Calls Ollama client (mocked)
     - Writes classified note to correct topic/subtopic folder
     - Relocates attachments
     - Updates DB records
   - Run against a test Ollama instance (reuse GPU spike's build if still running, or spin up CPU-only briefly)
   - Verify frontmatter is valid YAML

8. **Acceptance Criteria verification** (manual):
   - Ingest a real note (e.g., a PDF or web clip) via Story 1.1
   - Run batch sweep (`batch/worker.js`)
   - Verify:
     - Note ends up in correct `$VAULT_DIR/{topic}/{subtopic}/` folder
     - Frontmatter contains valid YAML, tags, topic, subtopic
     - Referenced images/PDFs are in sibling `.attachments/` folder
     - Markdown links are rewritten to point to new locations

## Known unknowns

1. **Prompt quality** — the few-shot prompt might need iteration to get consistent, valid JSON output for edge cases (very short notes, notes with code blocks, etc.). Plan for 1–2 iterations.

2. **Attachment detection** — Markdown link regex may miss some references (embedded iframes, non-standard markup). Accept in Phase 1; refine in later maintenance.

3. **Topic/subtopic taxonomy** — how strict should we be? Hardcode vault topics from `params.json`? Or allow LLM to suggest new subtopics? Propose: start strict (error if LLM suggests unknown topic), relax in maintenance if users need it.

4. **Retry logic** — Story 4.1 (batch queue) will determine max retries and backoff. For now, assume 1 attempt per job per sweep.

## Design Debt callouts

None anticipated — ADR15 and ADR10 already provide the architectural framework.

## Decisions (2026-08-31)

1. **Prompt format**: JSON output (structured, easier to parse than free-form text)
2. **Attachment handling**: Scan Markdown links, relocate files, rewrite paths (per ADR15)
3. **Error strategy**: Mark job failed, don't block pipeline; Story 4.1's retry logic decides re-runs
4. **Taxonomy**: Start strict, error if LLM suggests unknown topic
