# **SYSTEM-REQUIREMENTS-SPECIFICATION.md**

## **1\. Project Description**

The Personal Knowledge & Executive Assistant System is a privacy-first, locally hosted "second brain" designed to eliminate informational overwhelm. The system frictionlessly captures unstructured ideas, voice-to-text transcripts, links, documents, and email/calendar feeds. Using background overnight batch processing powered by a local LLM, it sanitizes, classifies, and indexes all content into a human-readable local Markdown vault (compatible with Obsidian) and a local RAG vector database. Rather than relying on static graph displays, the system proactively surfaces contextually relevant notes, daily schedule briefings, and prioritized email summaries to the user when needed.

## **2\. Functional Requirements Baseline (Phase 1\)**

| Code | Name | Abstract | Detailed Description & Acceptance Criteria   |
| :---- | :---- | :---- | :---- |
| **FR1** | Direct Structured Ingestion | Ingests native text and Markdown directly without transformation. | **Description:** Accepts plain text, voice-to-text transcripts, and .md files. **Acceptance Criteria:** 1\. Directly accepts raw text or Markdown input. 2\. Bypasses extraction/sanitization phases. 3\. Saves the file directly into the local Obsidian vault structure. |
| **FR2** | Unstructured Extraction & Sanitization | Converts URLs, PDFs, and rich media into clean Markdown. | **Description:** Processes URLs (stripping navigation, headers, and footers), PDFs, images (OCR), and Word docs into clean Markdown. **Acceptance Criteria:** 1\. Removes non-essential layout noise (HTML headers, menus, sidebars). 2\. Converts extracted body text into clean Markdown format. 3\. Output feeds directly into the classification pipeline. |
| **FR3** | Tagging & Classification Hints | Preserves user tags and applies LLM-assisted taxonomy. | **Description:** Accepts optional manual user tags during capture and uses them as primary hints for local LLM vault organization. **Acceptance Criteria:** 1\. Retains all user-provided tags without deletion. 2\. Local LLM appends supplementary taxonomy tags based on content. 3\. Files the .md note into the target vault directory based on classification. |
| **FR4** | Local Vault & RAG Indexing | Stores knowledge in Obsidian-compatible .md files and indexes vector embeddings locally. | **Description:** Maintains all storage as plain-text .md files in a local folder and updates a local vector database for RAG retrieval. **Acceptance Criteria:** 1\. All files remain strictly human-readable .md within a local directory. 2\. Local vector database generates and updates embeddings for new or modified notes. 3\. Vector search returns relevant note context for local LLM queries. |
| **FR5** | Overnight Batch Processing | Executes heavy LLM parsing, indexing, and email ingestion during background windows. | **Description:** Schedules non-urgent tasks (unstructured extraction, vector indexing, email digestion) to run locally in background batch runs (e.g., overnight). **Acceptance Criteria:** 1\. Queues raw inbox items for overnight processing. 2\. Executes batch pipeline locally without external API usage costs. 3\. Logs execution status for processed files. |
| **FR6** | Proactive Daily Briefing | Generates a daily Markdown report summarizing schedule, priority emails, and context. | **Description:** Parses email headers/important messages and calendar data overnight to produce a single daily summary note. **Acceptance Criteria:** 1\. Connects locally to retrieve email headers and calendar items. 2\. Filters and flags high-priority emails based on actionability. 3\. Generates a formatted Daily Report .md file in the vault before the user's day starts. |

| **FR7** | Ingestion UI | Web interface for submitting raw inputs | Provides web-based user interface to capture freeform text, URLs, or file uploads destined for the processing pipeline. | User submits text or files via UI form and receives immediate queue confirmation and job submission ID. |
| **FR8** | Search UI | Interface for querying vault and embeddings | Exposes a search bar supporting both keyword and semantic RAG search across indexed Obsidian notes. | Search query returns ranked note snippets with direct local note links within sub-second latency. |
| **FR9** | Ingestion Status UI | Monitors background pipeline state | Displays real-time status of current ingestion jobs, error logs, and batch processing queues. | Dashboard renders active, pending, and failed job counts with options to retry failed items. |


## **3\. Non-Functional Requirements (NFR)**

| Code | Name | Abstract | Detailed Description & Constraints | Acceptance Criteria   |
| :---- | :---- | :---- | :---- | :---- |
| **NFR1** | Host Runtime Environment | Windows 11 host with WSL2 integration | Core compute processes execute inside WSL2 on a single PC host. | System services (Node.js, Ollama) start and execute successfully inside WSL2 without requiring external cloud resources. |
| **NFR2** | Local Inference Engine | Ollama hosting llama3.2 | Ollama manages local LLM execution. Requires GPU passthrough in WSL2. | Executing ollama run llama3.2 inside WSL2 yields responses locally with GPU acceleration active and zero outbound network calls. |
| **NFR3** | Knowledge Base & Embeddings | Obsidian with Smart Connections | Obsidian manages local notes; Smart Connections maintains vector index (.smart-env). | Smart Connections successfully scans the Obsidian vault, generates vector embeddings, and stores them in local .smart-env files. |
| **NFR4** | Tool Protocol Integration | Smart Connections MCP Server | Exposes the vault vector index to external tools via Model Context Protocol. | MCP client (e.g., Claude Code or custom script) connects via stdio/HTTP, issues a vector query, and receives relevant note context. |
| **NFR5** | Orchestration Server | Node.js runtime environment | Runs background pipeline tasks, processing logic, and Web UI endpoints. | Node.js process starts on host, responds to health checks on designated port (e.g., http://localhost:3000), and routes pipeline jobs. |
| **NFR6** | Data Processing Script | Node.js script via local OpenAI SDK | Script calls http://localhost:11434/v1 for conversions, cleanup, and classification. | Script executes transformation jobs using OpenAI JS SDK configured with Ollama's local URL without throwing authentication or endpoint errors. |
| **NFR7** | User Interface | Web-based Management UI | Web UI hosted by Node.js for pipeline orchestration and monitoring. | Web UI loads in a local browser, displays real-time job status, and allows users to trigger/pause conversion pipelines. |
| **NFR8** | Resource Governance | WSL2 Memory & VRAM bounds | Constrained via .wslconfig to prevent Ollama and Node from starving Windows OS. | Memory allocation in .wslconfig caps WSL2 usage (e.g., max 16GB RAM) preventing Windows host OOM crashes during heavy LLM inference. |
| **NFR9** | Process Lifecycle | Service startup and process supervision | Managed dependency startup sequence (Ollama \-\> Node.js/MCP) via systemd/PM2. | Single launch command or system boot automatically starts Ollama first, confirms port availability, and then initializes Node.js/MCP services. |
| **NFR10** | Storage Synchronization | File lock and state management | Manages concurrent read/write locks on .smart-env across Windows/WSL file boundaries. | Simultaneous operations (Obsidian note updates while a background script reads embeddings via MCP) complete without sqlite/file-lock errors. |
| **NFR11** | Queue & Concurrency | Local inference rate limiting | Enforces single-worker or strict queue concurrency on Ollama processing jobs. | Script processes batch payloads sequentially or via queue (concurrency: 1), preventing Ollama memory overhead spikes or dropped HTTP sockets. |
| **NFR12** | Observability & Logging | Unified task logging and error handling | Captures script execution logs, LLM parse failures, and MCP tool call traces. | Execution logs write to stdout/file in structured JSON, logging failed JSON responses from LLM or MCP dropouts without terminating the main server. |
| **NFR15** | Structured Metadata & Job Queue Storage | Local SQLite database for Document/Status/Classification/Job tracking | Persists structured, queryable metadata (document lifecycle status, hierarchical classification, job queue/history) separate from the Markdown vault and .smart-env vector store, in a single local SQLite file. | Node.js orchestration server reads/writes the Document/Status/Classification/Job schema via SQLite without requiring a separate database server process. |
