## Phase 1 — Implement the code

Review target: the story's Design section (`documents/story/P2.9.md`, "Design") and all 18
acceptance criteria, against the seven files in `src/main/java/com/fourthbrain/convert/`. Concrete
gaps found by inspection, file by file:

### `MarkItDownConverter.java`

1. **The version probe never records a real version, and never checks it (AC15 is entirely
   unimplemented).** `performProbe()` (lines 77–124) runs `--version` but calls
   `pb`... via `DefaultProcessRunner`, whose `run()` sets `redirectOutput(Redirect.DISCARD)`
   (`DefaultProcessRunner.java:31`) — so the version string the process prints to stdout is thrown
   away before it can be read. `performProbe()` then hardcodes `String version = "markitdown";`
   (line 115) instead of a parsed value. Neither `expectedVersion` nor `versionCheck` is read
   anywhere in the class (confirmed by grep — zero matches). Design step 2 of "The startup probe"
   ("If `expected-version` is set and does not match: `version-check: fail` throws, `warn` logs at
   WARN, `off` skips") has no code behind it at all. This is the largest single gap: AC15 cannot
   pass under any configuration today.
2. **The probe never does its step 3 (the fixture round-trip).** Design step 3 of "The startup
   probe" calls for writing `probe-<uuid>.html` with a heading and a non-ASCII line, converting it,
   and asserting the Markdown contains `Prüfung` and `—` — this is what exercises the extras
   install, the `-o` write path and the Windows encoding trap before any actuator thread starts.
   `performProbe()` only runs `--version`; the conversion round-trip step does not exist.
3. **The probe uses the wrong timeout.** Design step 1 specifies a 10 s timeout for `--version`.
   `performProbe()` passes `properties.getMarkitdown().getTimeout()` (line 94), the full
   conversion timeout (120 s default), to the version check.
4. **`initialize()`'s failure message doesn't meet AC14.** AC14 requires the fail-fast log/exception
   to contain "the attempted absolute path and a remediation line"; Design step 5 of the probe adds
   "the full command line, the exit code, the stderr excerpt and the venv install command." The
   actual message (lines 47–51) is `"MarkItDown converter probe failed... Detail: %s. Install
   with: python -m pip install markitdown[extras]"` — a generic pip line, not the runbook's pinned
   install command, and it never names `properties.getMarkitdown().getExecutable()` or `.python()`,
   so the attempted absolute path AC14 requires is not in the message at all.
5. **`convert()` can return `null`, violating its own interface contract.** `performConversion()`
   (lines 199–281) is annotated `@SneakyThrows` with no `throws` clause, and its `catch (IOException
   e)` block (lines 269–270) only logs and falls through to `return null;` at line 280. The
   interface's Javadoc says "Never returns null, never returns blank" (`MarkdownConverter.java:8`),
   and the Design section gives every I/O failure a `Reason` (`IO_ERROR`) to throw instead. Any
   `IOException` during staging or reading output (e.g. a copy failure, a full disk) currently
   produces a silent `null` return rather than a `ConversionException`.
6. **`ProcessRunner.run()`'s declared `throws Exception` is not fully handled.** The interface
   (`ProcessRunner.java:15`) allows any `Exception`, but `performConversion` only catches
   `IOException`. A non-`IOException` (e.g. an `InterruptedException` propagating from inside a
   real implementation, or anything else) escapes `@SneakyThrows` as an undeclared checked
   exception, past `convert()`'s own `catch (ConversionException e)` / `catch (InterruptedException
   e)` handlers (lines 183–191), and out to the caller as a raw, undocumented exception type — a
   contract break against the interface's "throws ConversionException" signature.
7. **UTF-8 decoding is always lenient, never strict-then-fallback, and never logs the WARN Design
   step 12 calls for.** `new String(Files.readAllBytes(outputFile), StandardCharsets.UTF_8)` (line
   258) uses the default REPLACE action for malformed sequences silently; it never attempts a strict
   decode first, never catches `MalformedInputException`, and never logs at WARN with the path. The
   "malformed UTF-8 output" fake-runner scenario the story's own "Thread safety and tests" section
   calls for has no differentiated code path to exercise.
8. **No per-call directory is created, contrary to Design step 5.** `performConversion` stages
   `in-<uuid>.<ext>`, `out-<uuid>.md` and `err-<uuid>.txt` directly under the single shared
   `workDir` (lines 202–204) rather than "a per-call directory under `work-dir`." Cleanup still
   deletes the three files, so AC13's *observable* end-state (no leftover `in-*`/`out-*`/`err-*`)
   is likely still met, but there is no per-call directory to clean up at all — a deviation from
   the Design section worth a decision (accept the flatter layout, or add the subdirectory) rather
   than a silent drift.
9. **The kill sequence doesn't match Design step 9, and can leak descendant processes.** Design step
   9: "`destroy()` each of `process.descendants()` then the process, wait 2 s, `destroyForcibly()`
   anything left, wait again." `DefaultProcessRunner.killProcess()` (lines 53–72) instead calls
   `process.destroy()` on the parent only (line 55), sleeps 2 s, and — *only if the parent is still
   alive* — forcibly destroys descendants and the parent (lines 63–66). If the parent process exits
   within the 2 s grace period but a descendant it spawned (e.g. a helper process markitdown shells
   out to) does not, that descendant is never touched, because the `if (process.isAlive())` guard
   at line 63 checks only the parent. This is the concrete mechanism AC4's "no `markitdown` process
   is alive 10 s after `convert` returns" is designed to catch.
10. **Stderr excerpting reads the whole file before truncating, and drops Design's "first and last
    lines" nuance.** Line 233–236 does `Files.readAllBytes(stderrFile)` (whole file into memory)
    then `stderr.substring(0, 8192)` — a head-only truncation. Design step 10 says "read up to 8
    KiB... keep the first and last lines," which matters because Python tracebacks put the useful
    frame at the end. Low severity relative to items 1–9, but worth fixing in the same pass since
    it touches the same method.
11. **`application.yaml`'s `fail-fast` default disagrees with the story.** The story's own example
    (`documents/story/P2.9.md` line 113) shows `fail-fast: true`; the live config
    (`src/main/resources/application.yaml:103`) sets `fail-fast: false`. Not a code bug, but a
    behavioral default that silently differs from the documented one — worth a deliberate choice in
    phase 1, not a leftover.

  matches what the story's "Thread safety and tests" section asks tests to fake (exit code /

### `ConversionException.java`, `ConverterProperties.java`, `ProbeResult.java`, `MarkdownConverter.java`

  has the exact three-method signature. No structural gaps found in these four files — phase 1's
  corrections concentrate in `MarkItDownConverter.java` and `DefaultProcessRunner.java`.

## Phase 5 — Implement tests

Only after phase 3/4's checkpoint clears. The story's own "Thread safety and tests" section and its
18 acceptance criteria specify what's needed; below is that requirement broken into concrete
test-writing steps, each mapped to the criteria it satisfies. New package
`src/test/java/com/fourthbrain/convert/`, no Mockito, matching this repo's existing style
(hand-written fakes, assertions on captured behavior) per `plan-P2.9.md`'s step 4.

1. **A fake `ProcessRunner`** (`FakeProcessRunner` or similar test double) that can be configured
   to: return a non-zero exit code with canned stderr content; report `timedOut = true`; leave no
   output file; write an output file containing malformed UTF-8 bytes; write an output file that is
   whitespace-only; write an output file larger than a configured threshold. This one fake underpins
   most of the criteria below and needs no Python on the machine running it.

2. **`MarkItDownConverterTest`**, built against the fake runner:
   - AC2: `convert(path, "zip")` throws `UNSUPPORTED_FORMAT` even with `zip` added to
     `supported-extensions` in test config, and the fake runner records zero invocations.
   - AC3: `convert(path, "md")` and `convert(path, "txt")` throw `UNSUPPORTED_FORMAT`, zero runner
     invocations.
   - AC4 (fake half): with the fake configured to never signal completion (`timedOut = true`),
     `convert` returns within `timeout + 5s` with `Reason.TIMEOUT`; assert the fake recorded that a
     destroy/kill path was invoked. (The real-process half of AC4 — no `markitdown` process alive
     10 s after return, via `ProcessHandle.allProcesses()` — belongs to the live test class in item
     4 below.)
   - AC11: a source file sized above a test-configured `max-input-bytes` throws `TOO_LARGE` with
     zero runner invocations.
   - AC12: fake runner returns an output file above `max-output-bytes`; assert `OUTPUT_TOO_LARGE`
     and that the oversized file no longer exists afterward.
   - AC13: after the full suite runs, assert the configured `work-dir` contains no `in-*`, `out-*`,
     `err-*` files (or per-call directories, once phase 1 item 8 is decided).
   - AC14: with `executable` pointing at a nonexistent path and `fail-fast: true`, constructing the
     bean throws and the message contains the configured (fake) absolute path plus a remediation
     line; with `fail-fast: false`, construction succeeds, one ERROR is logged (capture via a test
     log appender or similar), and `convert` throws `UNAVAILABLE` with zero runner invocations.
   - AC15: with `expected-version` set to a value the fake's `--version` response won't match and
     `version-check: fail`, bean construction throws; with `warn`, construction succeeds and exactly
     one WARN is logged. This test cannot be written until phase 1 item 1 supplies the version-parse
     and comparison logic — flag it as blocked on that fix, not merely skipped.
   - AC16: ten concurrent `convert()` calls against the fake (configured to succeed) from ten
     threads all succeed, and a counter inside the fake never observes more than
     `max-concurrent-processes` concurrent invocations.
   - AC17: `ConverterProperties` binds every key from a test `application.yaml` fragment, including
     `timeout` written as `120s` and read back as a `Duration`.
   - Malformed-UTF-8 and whitespace-only output scenarios (Design step 12/13, no single AC number):
     fake runner writes malformed UTF-8 bytes → assert the strict-then-replace behavior once phase 1
     item 7 implements it, including the WARN log; fake runner writes whitespace-only output →
     assert `EMPTY_RESULT`.

3. **A package-private command-construction test**, called out explicitly by the story's "Thread
   safety and tests" section: test `buildConversionCommand` / `buildCommand` directly (package-private
   visibility, same package as the test) against source paths containing spaces and shell
   metacharacters (`&`, quotes), asserting the resulting `List<String>` never concatenates into a
   shell string and preserves the path as a single argument. This covers AC10's mechanism directly,
   independent of a live conversion.

4. **One live test class**, gated `@EnabledIfEnvironmentVariable(named = "FOURTHBRAIN_MARKITDOWN",
   matches = ".+")`, against fixtures committed under `src/test/resources/converter/` (which does
   not exist yet — create it as part of this phase):
   - A one-page digital PDF — smoke-checks a basic successful conversion.
   - A DOCX with two heading levels and a two-column table — AC9 (`# `, `## `, and a `|` row appear
     in the output).
   - An HTML fixture containing `Prüfung — 日本語` — AC8 (all three substrings survive round-trip
     through UTF-8 on the target OS; record the Windows run's outcome in the story's completion
     note, per AC8's own text).
   - An image-only PDF — AC6 (`EMPTY_RESULT`, not a blank success).
   - A PDF encrypted with a user password — AC5 (`CONVERTER_FAILED` or `EMPTY_RESULT`, non-blank
     `detail` under 8 KiB, and the same test method's *next* conversion call succeeds — proving the
     semaphore/permit release and per-call cleanup don't corrupt shared state after a failure).
   - A truncated PDF — AC7 (`CONVERTER_FAILED` with the converter's stderr excerpt present in
     `detail`).
   - A file whose name contains a space and `&` — AC10, run for real in addition to the unit-level
     command-construction test in item 3.
   - The real-process half of AC4 — a `timeout` of `1s` against a fixture large enough to exceed it,
     then assert via `ProcessHandle.allProcesses()` that no `markitdown` process is alive 10 s after
     `convert()` returns. This is the test that phase 1 item 9's kill-sequence fix must satisfy.
   These fixtures are synthesized, not drawn from any real inflow, so they're safe to commit — the
   story says so explicitly, and P2.8's corpus stays wherever P2.8 put it.
