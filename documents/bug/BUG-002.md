# Bug BUG-002 — A fresh clone will not start

## Symptom

`gradle bootRun` on a newly cloned repository fails during context initialization:

```
Caused by: java.sql.SQLException: path to 'data/fourthbrain.db':
           '/home/user/4thBrain/data' does not exist
```

The context refresh is cancelled and the application exits. Nothing is served.

## Root cause

`application.yaml` points the datasource at a relative path:

```yaml
url: jdbc:sqlite:data/fourthbrain.db
```

SQLite creates a missing database *file*, but not a missing parent *directory*. `data/` is an
excluded tree — git does not track it, so it is absent from any clone. The first thing the
application does with the datasource is run `schema.sql` through
`dataSourceScriptDatabaseInitializer`, which needs a connection, which needs the directory.

The failure is therefore guaranteed rather than intermittent: every clone hits it on first run,
and the only reason it has not been reported is that a working checkout accumulates `data/` once
and never loses it.

## Why it matters more than it looks

This masks other startup problems. While `data/` is missing, no amount of work on the beans
downstream can be verified, because the datasource aborts the refresh before any of them are
reached. P1.9's status was recorded as WIP partly because "Phase 1 does not boot" — and P1.9 turns
out to be fine. This defect was the visible failure.

## Fix options

| | Change | Note |
|---|---|---|
| A | Create the directory at startup, before the datasource initialises | An `ApplicationContextInitializer` or a `@Bean` ordered ahead of the datasource. Self-healing, no setup step. |
| B | Commit a `data/.gitkeep` | One file, no code. Fights the exclusion rule that keeps generated trees out of git. |
| C | Document a setup step | Cheapest, and the one that keeps biting new clones and CI. |

A is the only option that survives a clean CI checkout without a bespoke step. The same reasoning
applies to `vault/` and `tmp/`, which `application.yaml` also names and which no code currently
creates — worth handling in the same change rather than one directory at a time.

## Acceptance criteria

- [ ] `gradle bootRun` succeeds on a clone with no `data/`, `vault/` or `tmp/` directory
- [ ] The directories named in `application.yaml` exist after startup
- [ ] No manual setup step is needed before the first run
- [ ] Startup still fails loudly if a directory cannot be created — a silent swallow would trade
      this defect for a worse one

## Notes

Found while verifying P1.14. Not fixed there: P1.14 was scoped to the view layer, and widening it
to cover startup directories would have hidden a real defect inside an unrelated story. Worked
around locally with `mkdir -p data vault/incoming vault/indexing vault/raw tmp` to let the
verification proceed.
