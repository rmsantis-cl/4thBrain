# Bug BUG-004 — An octet-stream upload loses its extension and stops at `ingested`

## Symptom

A file uploaded through the UI is recorded with `mime_type` `application/octet-stream` and an **empty**
`extension`, is written to `tmp/` **without its suffix** — `notes.txt` lands on disk as `notes` — and
the pipeline stops at status `ingested`. The document never reaches the vault, and nothing reports an
error.

Evidence from the working database at the time of the fix:

```
id  name         ext      mime_type                 status
13  Retro skill  (empty)  application/octet-stream  ingested
```

Every document with a resolved type reached `indexed`. The single octet-stream document is the single
stuck one. `tmp/` held 23 extensionless files — `archive`, `document`, `document_001` … — each one an
upload that had its suffix stripped.

## Root cause

Three defects in `IngestionController.processUploadedFile`, in a chain where each one feeds the next.

**1. `application/octet-stream` was accepted as an answer.**

```java
String mimeType = file.getContentType();
if (StringUtils.isBlank(mimeType)) {
    mimeType = Files.probeContentType(Paths.get(originalName));
}
```

A browser posting a plain multipart upload declares `application/octet-stream` for most file types.
That is **not blank**, so `isBlank` is false and `probeContentType` never runs. The fallback was dead
code for exactly the case it was written to handle.

**2. The extension was derived from the MIME type, not from the file name.**

```java
String extension = getExtensionFromMimeType(mimeType);
```

`getExtensionFromMimeType("application/octet-stream")` hits the `default` branch and returns `""`. So
the extension was discarded — from the saved filename and from `Document.extension` — even though
`getOriginalFilename()` had it all along. The name is the one clue that survives a generic content
type, and it was the one thing not consulted.

**3. `Ingestor` then cannot type the document.** `isCompressedFile` and `isTextContent` both check
`mimeType` first and fall back to `extension`. With `application/octet-stream` and `""` they match
nothing, `doTheThing` returns null, and the document parks at `ingested` after `Actuator.run` stamps
the participle. Because a stage cannot record a failure (**DD-4**), the status reads like success.

## Fix

In `IngestionController`:

- **The extension comes from the original filename**, lowercased, with a leading dot only when there
  is something after it. `.gitignore` is a name, not an extension; `notes.` has no extension.
- **A new `resolveMimeType(declared, extension, originalName)`** decides the type in a stated order:
  a declared type that is not generic wins, because the client may know something the extension
  cannot say; otherwise the extension decides; otherwise `probeContentType`; otherwise
  `application/octet-stream`.
- **`isGenericType`** treats `application/octet-stream`, `binary/octet-stream`,
  `application/unknown`, `*/*` and blank as "no answer", which is what defect 1 got wrong.
- **`bareType`** strips parameters, so `text/markdown; charset=UTF-8` is stored as `text/markdown`.
- **A new `getMimeTypeFromExtension`** maps extension to type, covering the formats ADR28's converter
  accepts (pdf, docx, pptx, xlsx, epub, html) and the archives `Ingestor` routes to the `Extractor`
  (zip, gz, rar, 7z), so routing can be decided for a file that arrived as octet-stream.
- `getExtensionFromMimeType` is kept and now serves the opposite case: a name with **no** extension
  taking one from a type that is known.
- One DEBUG line records what was declared, what extension was found and what was resolved.

## Verification

`gradle build` green. Eight tests added to `IngestionControllerTest` covering octet-stream with a
known extension, `.pdf`, case-insensitive matching, a specific declared type winning, charset
stripping, an unknown extension, a name with no extension, and a `.zip` typed for routing.

Live, against a running application, uploading with `type=application/octet-stream` forced the way a
browser does:

```
mime-note.txt   -> mimeType text/plain,  extension .txt,  status indexed
mime-page.html  -> mimeType text/html,   extension .html, status indexed
```

Both reach `indexed`. Before the fix they would have been stored as `mime-note` and `mime-page` with
no extension and stopped at `ingested`.

## Notes

**Scope held deliberately.** The extension-to-type table duplicates `Extractor.guessMimeType`, which
has its own smaller copy. Extracting a shared utility would touch `Extractor.java`, which Story P2.3
rewrites against ADR28's `MarkdownConverter` seam, so the duplication is recorded here rather than
resolved in a change that was asked to stay in the controller.

**`newName` was not touched.** It computes uniqueness on the base name before the extension is
appended, so `notes.txt` and `notes.pdf` de-duplicate against a `notes` that never exists on disk.
Pre-existing, harmless today, and `plan-P2.2.md` introduces a shared `VaultNaming` helper that is the
right place to settle it.

**The 23 extensionless files already in `tmp/`** are residue from the old path. They are not cleaned up
by this fix, and the documents behind them are still parked at `ingested`. Re-ingesting them is a
choice, not a consequence.

**This is the second defect this month whose real damage came through DD-4** — a stage that cannot
report failure, so a stuck document reads as a finished one. BUG-004 was invisible until someone
looked at the database. Story P1.20's live status strip would have made it visible; it is also what
makes DD-4 worth closing.
