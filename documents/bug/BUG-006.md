# Bug BUG-006 — A clipped page routes back to the Clipper, forever

## Symptom

Submit any URL. The Clipper fetches it, creates a child document holding the HTML, and hands the child
to the Ingestor. The Ingestor routes the child back to the Clipper. The Clipper fetches the same URL
again, creates another child, and hands that one back.

This does not stop. Every cycle costs one HTTP request to the same URL, one new `document` row, two
files on disk (the Ingestor materialises the fetched HTML into `tmp` and archives a copy into `raw`),
and two `document_copy` rows. The Clipper's thread never returns to its queue, so a second URL
submitted behind the first is never processed.

It fires on **every** URL submission. There is no input that avoids it.

## Cause

Two correct-looking pieces of code that only misbehave together.

`Clipper.doTheThing` sets `sourceUrl` on the child it creates:

```java
Document childDoc = Document.builder()
    .parentId(doc.getId())
    .sourceUrl(sourceUrl)          // Clipper.java:72
    .name("clipped_" + doc.getName())
    .extension(".html")
    .mimeType("text/html")
    .content(fetchedContent)
```

That is deliberate and defensible. `Document.java:36` documents the field as "Where clipped content
was fetched from. Not a file location", and ADR26 decision 4 makes `source_url` the field of record
for a submitted URL. Keeping it on the child is provenance.

`Ingestor.nextStage` (`Ingestor.java:303-333`) evaluates `isUrl` **second**, before `isTextContent`:

```java
if (isArchive(doc))      { ... return "Extractor"; }
if (isUrl(doc))          { ... return "Clipper";   }   // Ingestor.java:308-311
if (isTextContent(doc))  { ... return "Indexer";   }
```

The child is `text/html` with `source_url` set. `isArchive` is false. `isUrl` is true, because the
field holds an absolute `http`/`https` URI. So the child never reaches the `isTextContent` test that
would send it to the Indexer, and the Ingestor sends it back to the stage that made it.

Neither class is wrong on its own. The Ingestor's ordering predates the Clipper producing children
that carry the field, and nothing states that `source_url` means "not yet fetched" rather than "came
from here". The ordering encodes the first reading; the Clipper writes the second.

## Why nothing caught it

`IngestorRoutingTest` asserts the routing table one document at a time and has no case for a document
that is both a URL and text — the combination only exists downstream of the Clipper. `PipelineFlowTest`
covers the full path for a text document, which short-circuits before the Clipper. No test drives a URL
through the Clipper and back into the Ingestor, and no test in the suite starts a real HTTP fetch.

## Fix

Two lines, and either of them stops it. They are not equivalent.

**Option A, recommended — a derived document is never re-clipped.** Qualify the Clipper row on
`parent_id`:

```java
if (isUrl(doc) && doc.getParentId() == null) {
    log.info("Document is URL - routing to Clipper: id={}", doc.getId());
    return "Clipper";
}
```

A document with a parent was produced by a stage of this pipeline, so its `source_url` is a record of
where its bytes came from and not an instruction to go and fetch them. The child keeps its provenance
and the routing decision stops being wrong. Nothing today sets `source_url` on any other kind of
derived document, so nothing else changes behaviour.

**Option B — drop `sourceUrl` from the child.** Delete `Clipper.java:72`. Simpler, and it loses the
one record of where the HTML came from. The parent still has it, so provenance survives one join, but
the child stops being self-describing.

Take A. If both are taken, A is the one carrying the meaning.

Either way, add the missing test: a `text/html` document with `source_url` set and `parent_id` set
routes to the Indexer, not to the Clipper. There is no `ClipperTest` at all today.

## Why the generation guard is not the fix

`documents/plan-P2.9-P2.3.md` adds `ingestor.max-generation` and a `generationOf` ancestry walk that
refuses to route to `Extractor` or `Clipper` past the limit. That guard would stop this loop at four
iterations instead of never.

It is still not the fix. The guard bounds the damage of a wrong routing decision; it does not stop the
decision being wrong. With the guard alone and nothing else, every URL submission would fetch the same
page four times, write eight files, create four documents, and then stop with a warning about
generation depth — which reads as a depth problem rather than as a routing bug, and would be diagnosed
as one. The guard is there for the loops nobody has thought of yet. This one has been thought of.

The plan also moves the convertible formats above the text test and puts `html`/`htm` among them
(ADR38 decision 5), which happens to make a clipped HTML child match the `Extractor` row before it
reaches the `Clipper` row. That masks this bug rather than fixing it, it depends on the child being
HTML, and it lands with a large piece of work that has a design gate and a spike in front of it. The
loop is live in the tree now.

## Acceptance criteria

- [ ] A URL submitted through `POST /api/ingest/capture` produces exactly one clipped child, and that
      child reaches the vault
- [ ] The child keeps `source_url` (under option A)
- [ ] A test drives a `text/html` document with both `source_url` and `parent_id` set through
      `Ingestor.nextStage` and asserts `Indexer`
- [ ] A test asserts that a top-level document with `source_url` and no parent still routes to the
      `Clipper`, so the fix has not disabled clipping
- [ ] `gradle build` green
