# Bug BUG-001 — UI Is Not Showing Up

## Symptom

`GET /` and `GET /chat` return no page. `/` redirects to `/chat`, and `/chat` 404s.

## Root cause

`UIController` is a `@Controller`, so its return value is a **view name** handed to a
`ViewResolver` — not a file path.

```java
@GetMapping("/chat")
public String chat() {
    return "index";        // view name "index"
}
```

`build.gradle` has no view technology. The dependency list is `spring-boot-starter-web`,
`-data-jpa`, `-validation`, `-logging`, plus SQLite, Commons and Lombok. There is no
`spring-boot-starter-thymeleaf`, no FreeMarker, no Groovy templates.

With no template engine, the only resolver present is Boot's default
`InternalResourceViewResolver`, which has no prefix or suffix configured. It forwards the view name
verbatim — `index`, not `index.html`. Nothing is mapped there, so the request 404s.

The page it should be showing, `src/main/resources/static/index.html`, is a static resource. It is
served by the resource handler at `/index.html` and is never reachable through view resolution.

### The `/` mapping makes it worse

Spring Boot serves `static/index.html` at `/` automatically — the welcome-page mechanism. That
would work today, unmodified. But `UIController` declares `@GetMapping("/")`, and a controller
mapping takes precedence over the welcome page, so the one URL that would have worked is
redirected into the one that cannot.

Deleting `UIController` outright would make `GET /` serve the UI correctly.

### Same defect in AdminController

`AdminController` returns `"admin"`, `"admin-db"` and `"api-docs"` (`AdminController.java:14,21,28`)
against `src/main/resources/templates/admin.html`, `admin-db.html` and `api-docs.html`. Those three
templates have no engine to render them and are dead files today. Five endpoints across the two
controllers are broken by the same cause.

## Not the cause

Ruled out while diagnosing, because the first draft of this bug assumed them:

- **Missing CSS/JS.** `static/index.html` is self-contained: one inline `<script>` at line 332 and
  `fetch()` calls against the REST API. It links no external stylesheet or script, so there is no
  missing `styles.css` or `client.js`. CLAUDE.md still lists them in the repository structure; that
  entry is stale.
- **Static resource configuration.** `application.yaml` overrides nothing under
  `spring.web.resources` or `spring.mvc`. Boot's defaults are intact and `classpath:/static/` is
  served normally.
- **Startup failure.** Unrelated. P1.9 does prevent the context from starting, but this defect is in
  the view layer and holds independently of it.

## Fix options

| | Change | Cost |
|---|---|---|
| A | `UIController` returns `"forward:/index.html"` from both mappings | Two lines. Keeps `/chat` working. Leaves AdminController broken. |
| B | Delete `UIController` | `/` works via the welcome page; `/chat` 404s. |
| C | Add `spring-boot-starter-thymeleaf`, move `index.html` to `templates/` | Fixes AdminController's three endpoints too; adds a dependency and makes `index.html` a template. |

### Decision: C

Taken 2026-09-07 and recorded as ADR25. Story **P1.14** carries it out.

A was the better fix on the evidence. None of the four pages contains a Thymeleaf attribute and no
controller method passes model data, so a template engine renders four files that have nothing to
render — C buys nothing on the day it lands.

It was chosen anyway, for the roadmap rather than the defect. `admin-db.html` is a database browser;
once it shows real rows it needs to render a collection server-side, and by then the static-file
approach would have to be unwound across every page that took it. Setting one convention over four
pages is cheaper than migrating a dozen later. ADR25 records the tradeoff, including this
counterargument, so the reasoning survives if it turns out to have been wrong.
