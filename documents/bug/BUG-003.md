# Bug BUG-003 — The left panel disappears on mobile

## Symptom

Opening the UI on a phone, or on any browser window narrower than 768px, shows the page with no
sidebar. There is no visible control that brings it back. Search, Ingest status and Admin become
unreachable; only whichever panel is active on load can be used.

## Root cause

Two independent defects in `src/main/resources/templates/index.html`, and **either one alone is enough
to produce the symptom**. Both predate P1.18 — they have been there since the Phase 1 skeleton (P1.7),
and P1.18 kept the topbar markup and the media query byte-identical.

**1. An inline style beats the media query.** The rule that is supposed to reveal the hamburger:

```css
@media (max-width: 768px) {
  .sidebar { display: none; /* … */ }
  .sidebar.open { display: flex; }
  .menu-btn { display: block; }      /* index.html:376 */
}
```

and the element it targets:

```html
<button class="menu-btn" style="display:none; …">☰</button>   <!-- index.html:400 -->
```

An inline `style` attribute outranks any stylesheet rule that is not `!important`, so
`.menu-btn { display: block }` never applies. The button is hidden at every viewport width. The
sidebar is hidden below 768px by the first rule, and the control that would open it is hidden by the
inline style — so the nav is gone with nothing to recover it.

**2. Nothing listens to the button.** No JavaScript in the file references `menu-btn`, `.sidebar` or
the `.open` class — the only occurrences are the CSS at `:356`, `:368`, `:376` and the markup at
`:391` and `:400`. Even with defect 1 fixed, tapping the hamburger would do nothing, because no
handler toggles `sidebar.classList.toggle("open")`. The `.sidebar.open` rule at `:368` has never had a
way to match.

The two together are why this reads as "the panel vanished" rather than "the menu button is broken".

## Scope

Narrower than it first looks, and worth stating so the severity is not overstated. `#panel-composer`
is the panel marked `active` on load, so on a phone the composer still works: capture by text, by URL,
by attachment, and asking the model are all reachable. What is lost is Search, Ingest status and the
Admin link.

P1.18 made this less severe rather than more. Before it, the default panel was Add File, so a phone
user could upload a file and do nothing else. The defect itself is unchanged.

## Fix options

| | Change | Note |
|---|---|---|
| A | Drop `display:none` from the inline style, move the whole inline style block into a `.menu-btn` CSS rule with `display: none` at wide widths and `display: block` under 768px, and add the toggle handler | Fixes both defects, and removes the inline style that caused the first one. The button's other eight declarations belong in the stylesheet anyway |
| B | Add `!important` to the media query rule and add the handler | Two lines. Leaves the inline style in place, so the next person hits the same specificity trap on the next property |
| C | Delete the hamburger and make the sidebar a horizontal strip under 768px | No toggle state to manage and nothing to leave stuck open. Costs vertical space on the smallest screens, and is a design change rather than a fix |

**A is the recommendation.** B works and preserves the defect's cause. C is defensible and should be a
decision rather than a bug fix if anyone wants it.

Whichever is taken, the handler has to close the sidebar after a nav item is tapped. The sidebar under
768px is `position: fixed` at `height: calc(100vh - 44px)` (`:356-366`), so it covers the page; leaving
it open after a selection hides the panel the user just chose.

## Resolution

Option A, in `index.html` alone.

- The eight declarations that were inline on the button became a `.menu-btn` rule in the `<style>`
  block, carrying `display: none`. The `@media (max-width: 768px)` block already held
  `.menu-btn { display: block }` and now wins, because there is no inline `style` attribute left to
  outrank it. The rule carries a comment naming this bug, so the next person adding a declaration
  puts it in the same place.
- The markup is `<button type="button" class="menu-btn" aria-label="Toggle navigation"
  aria-expanded="false">☰</button>`. No `style` attribute.
- `wireSidebarToggle()` binds the button to `setSidebar()`, which toggles `.open` on the sidebar and
  keeps `aria-expanded` in step. It runs once at startup, before `renderNav()`, because the button is
  static markup rather than something `renderNav` writes.
- `renderNav()` calls `setSidebar(false)` after switching panel, and binds the same call to the Admin
  link, which is an `<a>` rather than a panel button.
- No `th:inline` was added; `setSidebar` and `wireSidebarToggle` use no template literals, and the
  script block they sit in is the same one whose existing `${...}` literals must keep passing through
  Thymeleaf untouched.

Nothing else changed: the media query, the `.sidebar` rules and the panel markup are as P1.18 left
them.

## Acceptance criteria

- [x] Below 768px, a visible control opens the sidebar and a second interaction closes it
- [x] Tapping a nav item switches panel **and** closes the sidebar
- [x] Above 768px the sidebar is always visible and the hamburger is not
- [x] All four nav destinations are reachable on a phone-width viewport
- [x] No inline `display` style remains on `.menu-btn` (option A)
- [x] ADR25 held: the page stays in `templates/`, self-contained, and no `th:inline` is added to a
      script using template literals

**How far these were verified.** `gradle build` is green, and the last two criteria are structural —
they are true by reading the file. The first four describe what a browser does, and no test in this
repository renders a page. They are ticked on the code being right, not on having been watched: a
browser at a narrow viewport, or the same page on a phone, is still the check that closes them.

## Notes

Found on 2026-09-08 using the composer on a phone at `192.168.1.166:8080`, immediately after P1.18
landed. Not fixed in P1.18: that story was scoped to replacing four panels with the composer, and its
plan holds the topbar and the responsive block deliberately untouched so a broken render would be
bisectable to the composer. Fixing an unrelated pre-existing defect inside it would have hidden the
change under it.

Related: this is the second defect traced to `index.html` being a single self-contained page with
inline styles on individual elements. Not an argument to change ADR25 — it is an argument to keep
declarations in the `<style>` block, which option A does.
