# Plan — completing the UI entry points for data input

Merges `UI-ENTRY-POINTS-PLAN.md` (v1.0) into this file, which previously covered P1.11 alone. The
filename is narrower than the contents now; it is kept because P1.11 is stage 1 and the tracker,
INDEX and BACKLOG all link to this path.

Three data-input paths reach the vault: a file, a block of text, a URL. One works. This is the route
to all three working, behind whatever front end the composer spike settles on.

## What "all UI entry points" actually costs

P1.11, P1.13 and P1.17 do not finish the job on their own, and it is worth being clear about that
before starting rather than discovering it at the end.

- **P1.11** gives the pipeline a working entry point. Nothing user-visible changes.
- **P1.17** is a spike. Its own scope section says *"No production code lands under P1.17"* and its
  acceptance criteria end with *"Follow-on story: Implementation storied separately, blocked by
  P1.13."* It produces a decision, not a screen.
- **P1.13** implements `/api/ingest/text` and `/api/ingest/url`. After it, all three endpoints work
  and the existing three panels drive them.

So those three stories deliver every entry point *as an endpoint*, with the current three-panel UI in
front of them. The single composer — the thing that makes them feel like one entry point — is the
spike's follow-on story, which does not exist yet. This plan carries it as **stage 4 (P1.18)** and
recommends creating it when the spike reports. If you would rather not add a story, the alternative
is to widen P1.17 to allow production code, which trades the spike's throwaway-prototype property
for one fewer backlog row. The stage-4 route is better: the spike is half a day, and letting it land
production code removes the reason it runs before P1.13.

## Sequence

P1.17 has no dependencies and touches nothing under `src/main`, so it runs alongside stage 1 rather
than after it. The critical path is P1.11 → P1.13 → P1.18; the spike has to land before P1.13 starts,
because what the endpoints accept depends on what the composer sends.

```
stage 1   P1.11  Coordinator entry point          ─┐
stage 2   P1.17  Composer spike (parallel)        ─┴─→  stage 3  P1.13  text + url endpoints
                                                                    └─→ stage 4  P1.18  composer UI
```

Findings that survive from the original P1.11 plan:

- **The NPE is latent, not live.** Nothing on the current path logs a `Message`, so `toString()` is
  never reached. It fires the first time someone writes `log.debug("... {}", message)` while
  debugging something else. A trap, not a crash.
- **`sendMessage` has a second unguarded dereference** the story does not mention:
  `get(actuator).getQueue()` NPEs when the name is unregistered. `Actuator.run()` got a null check
  for this in P1.9; `sendMessage` never did.
- **`Message.builder()` never stamps `createdAt`.** Lombok's `@Builder` leaves it null at
  `Actuator.java:97`, `Clipper.java:144` and `Extractor.java:206`. Only the explicit 3-arg
  constructor sets it, and that constructor is the one being deleted.
- **`Message.id()` misspells its own output** — `"Mesasge[...]"`, `Message.java:45`.

### Correction carried into this merge

`UI-ENTRY-POINTS-PLAN.md` said the original plan's code sketches were dropped because they called
`DocumentService.getDocumentById` and `setStatus`, and "neither the class nor the methods exist".
**That is wrong.** Both exist: `DocumentService.java:40` returns `Optional<Document>` from
`getDocumentById`, and `:105` is `setStatus(Document, String)`. `Actuator` already autowires
`DocumentService` and calls `setStatus` on every hop.

The switch to `DatabaseService` is kept anyway, for the reason that actually holds: `DatabaseService`
is the synchronized one (ADR17, brief serialized transactions), it is what `IngestionController`
already injects, and `Coordinator.startChain` is a write on the request thread. `DocumentService` is
unsynchronized.

That leaves a real inconsistency worth naming rather than inheriting: **two services write
`Document.status`** — `DatabaseService.updateDocumentStatus` (synchronized) and
`DocumentService.updateDocumentStatus` (not), with the actuator run loop using the unsynchronized
one on every stage transition. ADR17 is either being honoured or it is not. Add a line to ADR26
saying which service owns status writes, or log it in `documents/DESIGN-DEBT.md`. Do not silently
pick one per call site.

### New finding — a URL submission cannot reach Clipper as P1.13 describes it

P1.13's acceptance criteria say a URL submission produces *"a document with `source_url` set and no
`document_copy` row"*. Built that way, the document dies at the first hop:

- `Ingestor.isUrl(doc)` tests `doc.getContent()`, not `doc.getSourceUrl()` — `Ingestor.java:87-100`.
- `Clipper.doTheThing(doc)` also reads the URL from `doc.getContent()` — `Clipper.java:53-57` — and
  stamps `sourceUrl` only on the *child* document it creates — `Clipper.java:71`.

A parent with `sourceUrl` set and `content` empty matches neither `isUrl` nor `isTextContent`, so
`Ingestor` logs *"Document type not recognized"*, returns null, and the chain stops with the document
parked at `ingested`. No error, no retry, nothing in the UI.

This is a design decision, not an implementation detail, so it goes in ADR26 with the rest of the
entry contract. Recommendation: **`source_url` is the field of record for a submitted URL**, and
`Ingestor.isUrl` and `Clipper` are changed to read it. `content` then keeps one meaning — the
document's text — and a URL document legitimately has none until Clipper fetches it. The cost is two
small edits inside stage 3, both unavoidable if P1.13's criteria are to be met at all.

### Out of scope, recorded so it does not read as a regression

`getStatusCounts()` returns queue depths keyed by actuator class name (`Ingestor`, `Extractor`),
while `StatusController.java:22-26` looks up `ingesting`, `extracting`, `indexed`. Every key misses,
so `/api/status` returns five zeros whatever the pipeline is doing. That is Story P1.12's entire
subject. Nothing here fixes it, and nothing here may make it worse.

## Design decisions to take first

`.claude/rules/design-before-implementation.md` requires a design artifact before code. Two ADRs are
reserved by number and neither is written.

**ADR26 — the pipeline's entry contract** (write before stage 1):

1. `startChain(long documentId)` is the only entry point. `sendMessage` is deleted.
2. `Message.from` is legitimately optional, because a message can originate at the REST boundary,
   outside any actuator. `id()` and `toString()` render a null sender rather than reject it.
3. The Coordinator registry becomes instance state on the `@Component`, not static.
4. A submitted URL is carried on `Document.sourceUrl`, and `content` stays empty until something
   fetches it.
5. One service owns `Document.status` writes, named explicitly, per the correction above.
6. One response shape across all three ingest endpoints (see stage 3).

Decision 3 is the one that needs its reasoning written down, because the cheap version does not work.
Clearing a static registry on context close gives no test isolation: Spring caches test contexts, so
when a second `@SpringBootTest` with different properties builds a second context, the first is still
open and its actuators are still registered. Both sets live in one static map and `get("Ingestor")`
returns whichever registered first. Only per-context state satisfies the acceptance criterion.

**ADR27 — the composer's routing decision** (written by stage 2, from the spike's result).

Numbering: 26 is P1.11's, 27 is the spike's, 28 is taken by the P2.8 converter decision.
`documents/story/P1.17.md:53` and `documents/design/SPIKE-UNIFIED-COMPOSER.md:192` said 26 and have
been corrected to 27.

`documents/DESIGN-DEBT.md` does not exist. The rule names it, so create it when the first gap needs
logging, rather than as a step of its own.

## Stage 1 — P1.11, one entry point

### Coordinator

```java
@Component
public class Coordinator {

    @Autowired
    private DatabaseService databaseService;

    private static final String FIRST_STAGE = "Ingestor";

    // Per-context, not per-JVM: two Spring contexts in one JVM (which is what
    // the test cache produces) must not see each other's actuators (ADR26).
    // Still concurrent: ActuatorManager registers on the main thread at startup,
    // every actuator thread reads on each routing hop.
    private final Map<String, List<Actuator>> registry = new ConcurrentHashMap<>();

    public void register(Actuator a) { ... }                // was static
    public List<Actuator> instancesOf(String name) { ... }  // was static
    public Actuator get(String name) { ... }                // was static

    public void startChain(long documentId) {
        Document doc = databaseService.getDocument(documentId);
        if (doc == null) {
            throw new IllegalArgumentException("startChain: no document with id " + documentId);
        }
        Actuator first = get(FIRST_STAGE);
        if (first == null) {
            throw new IllegalStateException("startChain: no '" + FIRST_STAGE + "' registered");
        }
        databaseService.updateDocumentStatus(documentId, first.getGerund());
        first.enqueueMessage(Message.to(first, doc));
        log.info("chain started doc={} -> {}", documentId, first.getName());
    }
}
```

`DatabaseService.getDocument` returns a bare null rather than an `Optional`, so the check is
explicit. `startChain` sets the first gerund before enqueueing: the run loop sets it again on pickup,
which is idempotent, and the point is that a document reads as `ingesting` between the HTTP response
and a thread reaching it, rather than sitting at `New` with nothing to say it is queued.

`sendMessage` is deleted.

### Call sites of the previously static registry

Four, all Spring-managed, so this is injection rather than plumbing:

| File | Now | After |
|---|---|---|
| `ActuatorManager.java:81` | `Coordinator.register(a)` | `@Autowired Coordinator` field → `coordinator.register(a)` |
| `Actuator.java:90` | `Coordinator.get(n)` | `@Autowired` field on the abstract base, inherited by all five subclasses |
| `Clipper.java:136` | `Coordinator.get("Ingestor")` | inherited field |
| `Extractor.java:198` | `Coordinator.get("Ingestor")` | inherited field |

Actuators are built through `ObjectFactory` (P1.9), so `@Autowired` on the base is populated the same
way `service` already is. Injection completes in `ActuatorManager`'s `@PostConstruct` phase A, before
registration in phase B and well before threads start in phase C — the ordering P1.9 established
already covers this.

### Message

Replace `@Data`/`@Builder`/`@AllArgsConstructor` and the public constructor with `@Getter` and two
static factories, so `createdAt` cannot be forgotten and `from` cannot NPE:

```java
public static Message to(Actuator target, Document doc)                  // external origin, from == null
public static Message between(Actuator from, Actuator to, Document doc)
```

- `id()` renders a null sender as `external` instead of dereferencing it, and the `Mesasge` typo goes.
- `@Data` goes with it. It generates `equals`/`hashCode` across an `Actuator` (a `Thread`) and a JPA
  entity, for a value that is never compared or used as a key. `@Getter` is what the class uses.
- Three call sites move to `Message.between(...)`: `Actuator.java:97`, `Clipper.java:144`,
  `Extractor.java:206`. `startChain` is the only caller of `Message.to(...)`.

## Stage 3 — P1.13, the text and URL endpoints

### submitText

Create a Document with `content` set to the posted text, `mimeType` `text/plain`, no copy row —
nothing is on disk — then `coordinator.startChain(saved.id())`. `Ingestor.isTextContent` already
recognises `text/plain` and routes to Indexer, so no actuator change is needed on this path.

### submitUrl

Create a Document with `sourceUrl` set to the posted URL, `content` empty, no copy row, then start the
chain. Then, per ADR26 decision 4:

- `Ingestor.isUrl(doc)` tests `doc.getSourceUrl()` instead of `doc.getContent()`.
- `Clipper.doTheThing(doc)` reads the URL from `doc.getSourceUrl()`, and keeps stamping `sourceUrl` on
  the child it creates.

Both are a few lines. Without them the endpoint returns 200 and the document goes nowhere, which is
the failure the front end cannot see.

### One response shape, applied three times

`/file` returns `id`; the tests and the front end both read `jobId`, which belonged to the Job design
removed in Phase 1. Pick one shape in ADR26 and apply it to all three endpoints:

```json
{ "id": 42, "status": "ingesting", "message": "Queued" }
```

`index.html:484` and `index.html:507` read `data.jobId` and will print `undefined` until they are
changed with it. The three panels stay as they are otherwise — replacing them is stage 4.

### Tags

All three panels post a `tags` field and every endpoint ignores it. Leave it ignored, and let the
spike's answer on where tags live drive it in stage 4. Wiring tags to `linkDocumentToTag` here would
be built against a UI about to be replaced.

### Tests

Delete the `@Disabled` annotations from stage 1 and rewrite `IngestionControllerTest` against the
current contract: `id` rather than `jobId`, `databaseService.create(...)` rather than
`createDocument("text", ...)`, and `coordinator.startChain(...)` as the entry point. All 23 pass, or
the ones that assert a removed design are deleted rather than adjusted.

Add two integration checks: a text submission reaches Indexer, and a URL submission reaches Clipper
with `sourceUrl` set and no `document_copy` row.

running app. The text document ends at `indexed`; the URL document produces a child document with

## Stage 4 — P1.18, the composer itself

To be created by the spike, blocked by P1.13. It builds the option the spike chose into
`index.html` — one composer, the URL rule, the attachment behaviour, the receipt feed — and collapses
the three ingest panels into it. Constraints already fixed: ADR25 (page in `templates/`, controller
returns the bare file name), no `th:inline="javascript"` on any script using template literals, and no
bundler or framework.

This is the stage that makes the entry points feel like one, and the goal is not met without it.
