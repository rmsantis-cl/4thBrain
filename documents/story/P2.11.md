# Story P2.11 — Measure classification quality across candidate models

## Problem

Nothing in this project has ever checked whether the Classifier produces the right answer.

Story P2.4 closed with 33 tests and its own completion note records why that is less than it sounds:
every one of them runs against a hand-written fake `OllamaClient`. They prove that a well-formed
reply is parsed correctly, that a malformed one does not stop the pipeline, and that tags are
normalised the way ADR31 specifies. They say nothing about whether the tags coming back describe the
document.

`application.yaml` names `mistral` because that is what someone wrote down first. It has never been
compared against anything. `design/SPIKE-LOCAL-MODEL-SELECTION.md` argues for replacing it with a
4B-class model on hardware grounds, and the argument is sound as far as it goes, but it reasons about
throughput and quantisation rather than about output. If the smaller model tags worse, the spike's
recommendation is wrong and nothing currently on file would reveal that.

So there are two open questions and only one of them has an owner. P2.10 pins a tag and stops it
floating. This story asks whether the pinned tag is the right one.

**Except that P2.10 closed without pinning one.** Ollama 0.33.3 is installed and answering on
`localhost:11434`, and `ollama list` holds `devstral:24b` and `gemma4:12b`. `mistral` was never
pulled, so `application.yaml` names a model the server cannot serve and the first real Classifier
call gets a model-not-found. That makes this story's job larger by one item: it does not only choose
between candidates, it produces the first tag the configuration can actually resolve. Somebody may
pin one of the two local models by hand before then, to get a working Classifier; that is a
placeholder and not this story's answer.

The two local models also change the candidate set. Neither was chosen for this pipeline — `devstral`
is a coding model — and both are large for CPU inference, which the spike's throughput table puts at
a few tokens per second. `gemma4:12b` is worth carrying as the upper-bound arm anyway, because it is
already on disk and costs nothing to include.

ADR31 also lists "tag vocabulary drifts" as an accepted consequence — nothing constrains the model to
a controlled vocabulary, so `tag` grows a row per phrasing the model invents. That is recorded as
acceptable at personal-vault scale and as the first thing to revisit if search gets noisy. There is
no measurement behind either half of that sentence.

## Decisions to settle

1. **What counts as a correct tag.** There is no gold standard anywhere in the project. Three ways to
   make one, and they measure different things:
   - The user hand-labels a fixture set. Expensive per document and the only option that measures
     correctness rather than a proxy for it.
   - Inter-model agreement — treat a tag as good when several models produce it. Cheap, and it
     measures consensus. Three models sharing a bias agree with each other and are all wrong
     together.
   - Retrieval — does the tag help find the document again later. The right long-run measure and
     unavailable now, since search over tags is not built.

   Recommended: hand-labelling at small n. Twenty to thirty documents is enough to separate models
   that differ by a lot, and models that differ by a little do not justify the switch anyway.

2. **Fixture composition.** The set has to look like real inflow or the result does not transfer.
   P2.8 needs the same census from the converter's side — its trigger 1 is a format count that has
   never been run. Run it once and let both stories read it.

3. **Metrics.** Precision and recall against the labelled tags. `topic` is a free noun phrase, so an
   exact match is the wrong test and it needs a judgement per document instead. Two more worth
   capturing because they are nearly free: the size of the tag vocabulary after the full set, which
   is ADR31's drift consequence made measurable, and the share of replies that fail to parse, which
   is what `response_format: json_schema` is supposed to drive to zero.

4. **Where the harness lives.** This is not production code and does not belong in `src/main`. Two
   candidates: a script under `scripts/`, which has its own INDEX and no build coupling, or a
   `@Disabled` JUnit class that a person runs deliberately. The second reads better and drags a live
   Ollama dependency into a test tree that `gradle build` runs on every branch. Load-bearing enough
   to belong in the ADR rather than in whoever writes it first.

5. **Whether structured output is a variable or a constant.** The spike argues that
   `response_format: json_schema` matters more than the model choice. If that holds, the experiment
   is a grid of models against structured-output on and off, and not a list of models. If it does not
   hold, that is itself a finding worth having, because ADR31's balanced-brace parser exists to
   absorb exactly the failure the schema is meant to prevent.

Reserves **ADR34**. The reservation list in `BACKLOG-TRACKER.md` had 34 as the next free number.

## Change

1. Run the format census once, and record it where P2.8 can read it too.
2. Assemble the fixture set from real documents matching that mix, and hand-label tags and a topic
   for each. The labels are the artifact with the longest life here; keep them in the repository.
3. Build the harness per decision 4. It reads the fixtures, calls Ollama once per document per
   configuration, and writes a table.
4. Run the grid: the spike's 4B recommendation, one 8B model, and `gemma4:12b` as the upper bound
   since it is already local, each with structured output on and off if decision 5 says so. There is
   no incumbent arm — `mistral` is named in the configuration and installed nowhere, so pulling it
   to defend a choice nobody made is wasted time. Include it only if someone wants the configured
   value measured for the record.
5. Record wall time per document alongside the quality numbers. The spike predicts a 4B model is
   roughly twice as fast as an 8B on this hardware, and that prediction should either hold or be
   corrected.
6. Write the result as ADR34: which model, on what evidence, and what would reverse it.
7. Update `application.yaml` and P2.10's pinned tag if the answer differs from what is pinned.

## Acceptance Criteria

- A labelled fixture set exists in the repository, with the number of documents and how they were
  chosen recorded
- The harness runs from a documented command and produces the same table twice on the same inputs,
  or records why it cannot
- Precision and recall per model are on file, with the raw per-document output kept so a disagreement
  can be inspected rather than re-run
- Tag vocabulary size per model is recorded, giving ADR31's drift consequence a number
- Parse-failure rate is recorded with structured output on and off
- Wall time per document per model is recorded, on the machine named in P2.10's runbook
- ADR34 states the choice, the evidence, and its reversal conditions
- `application.yaml` names the chosen tag, and that tag appears in `ollama list` — the check P2.10
  did not make, and the reason the Classifier would fail on its first real call today

## Out of Scope

- Pinning the tag, installing Ollama, and the runbook. All P2.10's
- The hardware argument. `design/SPIKE-LOCAL-MODEL-SELECTION.md` owns it, and this story tests its
  conclusion rather than restating it
- A controlled tag vocabulary. Measuring drift is in scope; constraining it is a design change to
  ADR31 and needs its own story
- Prompt tuning. Changing the prompt and changing the model at the same time makes both results
  unreadable. Hold the prompt fixed at whatever P2.4 shipped, and note that a prompt experiment is
  the obvious follow-on
- Retrieval quality. The right long-run measure of a tag, and it needs search over tags, which is not
  built
