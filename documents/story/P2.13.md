# Story P2.13 — Extraction failure statuses

## Why this story exists separately

Story P2.9 wrote a binding contract mapping `ConversionException.Reason` to a terminal document
status, and Story P2.3 copied it verbatim as its own. Neither of them can be implemented, and the
reason has nothing to do with conversion.

`Actuator.run()` stamps the participle one line after `doTheThing` returns:

```java
String n = doTheThing(d);                   // Actuator.java:89
service.setStatus(d, getParticiple());      // Actuator.java:90
```

Anything the Extractor writes to `Document.status` is overwritten with `extracted` before the next
queue item is taken. Throwing instead is worse: `run()` catches it as "Main loop error"
(`Actuator.java:113-115`), skips the participle stamp, and leaves the document at `extracting` — an
in-progress status with no thread coming back for it, which is exactly what P2.9's own rules forbid.

That is **DD-4**, it lives in `Actuator.java`, and `Actuator.java` is frozen while the Phase 2 plans
are in flight. `documents/plan-P2.9-P2.3.md` therefore carves the failure statuses out of P2.3 rather
than blocking the whole story on a file it must not open. P2.3 delivers the conversion path with an
interim that logs the reason and nothing else; this story delivers the contract.

## What P2.3 leaves behind

On conversion failure the Extractor creates no child, logs the `Reason` and the `detail` at ERROR, and
the original stays in `raw`. The document reads `extracted`, indistinguishable from a success.

**There is no queryable failure signal in the interim.** The obvious one — parents at `extracted` with
no child — does not work under ADR38, because zero children is a legitimate outcome: an archive of
directories produces none, and a scanned PDF that yields images but no text produces children that are
all images. The query cannot separate a failed conversion from an empty archive, and nothing else
survives: `status` is stamped by the run loop, `content` is empty either way, and no column holds a
reason. What is left is a review list for a person, and the reason is in the log.

## The contract to implement

Copied from P2.9, unchanged, and it is what this story is for:

| `ConversionException.Reason` | Status | Why |
|---|---|---|
| `UNSUPPORTED_FORMAT` | `EXTRACTION_UNSUPPORTED` | queryable backlog of formats to add a converter for |
| `EMPTY_RESULT` | `EXTRACTION_EMPTY` | the scanned-PDF case; queryable backlog for a later OCR story |
| `TIMEOUT`, `CONVERTER_FAILED`, `TOO_LARGE`, `OUTPUT_TOO_LARGE`, `IO_ERROR`, `UNAVAILABLE` | `EXTRACTION_FAILED` | retry candidates once a human has looked |

Three rules follow:

- No failure path leaves a document in an in-progress status. The terminal status and the reason
  detail are written in the same transaction, before the next queue item is taken.
- Nothing else in the pipeline moves a document out of `EXTRACTION_*` on its own. These are terminal
  until a retry command or an OCR story moves them deliberately.
- The `catch` sits inside the actuator's loop, not around the thread body. One bad document does not
  end the thread.

## What has to be decided before this can start

1. **How a stage signals failure.** `doTheThing` returns the next actuator's name. Saying "I failed"
   means a sentinel return, an exception contract, or a result type, and each of those changes every
   actuator at once. This is DD-4's question and this story does not get to answer it alone.
2. **Whether the in-memory `Document` and the row stay in step.** DD-1 is tangled with DD-4 in the
   same three lines: `DatabaseService.updateDocumentStatus` reloads and saves a different object than
   the one travelling in the `Message`.
3. **Where the reason detail is stored.** `Document` has no field able to hold it. A `statusReason`
   column is the obvious answer and it is not free: `schema.sql` runs `CREATE TABLE IF NOT EXISTS`
   under `ddl-auto: validate`, so a new column reaches no existing `data/fourthbrain.db` and fails
   context startup on validation. Whatever this story does about that is the pattern every later
   schema change inherits, so it is worth deciding properly rather than in a commit.

## Acceptance criteria

- A conversion throwing each of the eight `Reason` values leaves the document at the mapped status,
  with a non-blank persisted reason detail under 8 KiB.
- No document is left at `extracting` by any failure path, including a `RuntimeException` from inside
  the converter.
- A document at any `EXTRACTION_*` status is not routed onward and is not classified.
- The Extractor thread processes the next document successfully in the same test that produced a
  failure.
- The query "documents whose conversion failed, and why" is answerable from the database alone,
  which is the thing the interim cannot do.
- An existing database created before this story starts still passes `ddl-auto: validate`.
- `gradle build` green.

## Out of scope

- Retrying. A document at `EXTRACTION_FAILED` sits there until something deliberate moves it, and
  building the thing that moves it is a later story.
- OCR. `EXTRACTION_EMPTY` is the backlog an OCR story would read; it is not this story.
- Failure statuses for the other actuators. DD-4 is pipeline-wide and the Indexer and Classifier have
  the same problem, but widening this story to all of them makes it a rewrite of the run loop with a
  conversion example attached.
