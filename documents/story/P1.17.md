# Story P1.17 — Spike: A Unified Composer

## Why This Spike Exists

The UI has six panels behind a nav: Add File, Add Text, Add URL, Search, Ingest Status, Chat with
Llama (`index.html:366-433`). Three of them do the same thing — put something into the vault —
and are separate only because the transport differs. The user picks a panel before knowing which
one applies.

The proposal is one screen: a text area, a row of buttons, `[+]` to attach a file, and URL mode
turning itself on when the input parses as a URL. Chat with Ollama in the same box.

## The Question to Answer

Auto-detection separates a file from a URL from prose, because those differ in form. It cannot
separate "save this note" from "ask this question" — both are prose in the same box. That routing
decision is what the spike is for, and it is not symmetric: chat misrouted to capture leaves junk in
the vault, capture misrouted to chat loses the note.

Five options are analysed in `documents/design/SPIKE-UNIFIED-COMPOSER.md`:

- **A** — Capture/Ask mode toggle beside the composer
- **B** — one box, two send buttons (`Add`, `Ask`) — the going-in favourite
- **C** — a `?` or `/ask` sigil, useful only as an accelerator on top of A or B
- **D** — infer intent from the text, rejected up front (silent, asymmetric failures)
- **E** — unify the three ingest paths only, leave Chat as its own panel (the fallback)

## Timebox

Half a day. Prototype code lives in `spikes/unified-composer/` and is throwaway.

## Acceptance Criteria

- **Prototype:** Options A and B both built against stubbed endpoints, with URL detection working
- **Routing decision:** One option named, with the reasoning and what would overturn it
- **URL rule:** Written precisely enough to implement — trigger, timing, override
- **Composition answers:** Text plus file, several files at once, where tags live, whether the mode
  resets after each send
- **Status feed:** A statement on whether the receipt feed needs per-document status, and which
  story owns that endpoint
- **Screen sketch:** Final layout, including what happens to the nav
- **ADR:** Decision recorded in `documents/design/ADRS.md` as ADR27
- **Follow-on story:** Implementation storied separately, blocked by P1.13

## Scope

- No production code lands under P1.17
- Search stays its own panel — folding it in adds a fourth meaning to Enter
- No bundler and no front-end framework; `index.html` stays a self-contained page (ADR25)

## Dependencies

None for the spike. It prototypes against stubs and needs no working pipeline.

The implementation story it produces will be blocked by **P1.13**, since `/api/ingest/text` and
`/api/ingest/url` both return `{"not":"implemented"}` today, and by **P2.1/P2.4** for a real Ollama
reply. Running the spike *before* P1.13 is deliberate: what those endpoints should accept depends on
what the composer sends.

## Key Risks

- **Generality backfires:** four intents through one control can need more chrome than the six panels
  it replaces; option E is then the answer
- **Silent misrouting:** the reason option D is rejected rather than measured
- **Stubbed prototype:** interaction can feel right at zero latency and wrong against a real Ollama
  call; the slow-response case must be designed unobserved
- **Scope creep into search:** tempting once the composer exists, out of scope
