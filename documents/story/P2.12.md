# Story P2.12 — Runtime model resolution from `ollama ps`

## Status

**COMPLETED 2026-09-08.** Implemented from ADR35 in one pass. `gradle build` green at 106 tests, 0
failures, 2 skipped — the two are `PipelineFlowTest`, disabled against BUG-005 and unrelated.
`OllamaHttpClientTest` went from 6 tests to 12.

Three files changed: `OllamaHttpClient.java` (model resolution, the derived native root, the
nothing-loaded error, `isAvailable`), `application.yaml` (`ollama.model` deleted, with the reason in
a comment where the key used to be), and the test class.

**The `/api/ps` response shape was checked against the running server**, not assumed: it returns
`{"models":[{"name":"devstral:24b","model":"devstral:24b",…}]}`, which is what `parseLoadedModels`
reads. `name` and `model` carry the same value there, and the parser prefers `name` with `model` as
the fallback.

**No live round trip.** Every test runs against `MockRestServiceServer`, so the client still has
never called a real Ollama — the same gap P2.1 closed with. Exercising it needs the application
running, and the only model currently loaded is `devstral:24b` at 37 GB resident on a 32 GB machine,
which pages on every token. [[P2.11]] is where a live call gets made against a model chosen to fit.

One acceptance criterion is covered by the existing code rather than by a new test: an unreachable
Ollama produces the unreachable-service error, because `resolveLoadedModel` catches
`ResourceAccessException` the same way `send` always has.

## Problem

`application.yaml` names `ollama.model: mistral`, and `mistral` is installed nowhere. P2.10 closed
having established that: `ollama list` on the development machine holds `devstral:24b` and
`gemma4:12b`. Every real Classifier call would come back model-not-found.

The value has been wrong since the skeleton and nothing caught it, because nothing in the project has
ever asked the server for a model. P2.4's 33 tests use a hand-written fake `OllamaClient`; P2.1's use
`MockRestServiceServer`. A configured model name is a value that is never wrong until it is used, and
it has not been used yet.

Story P2.11 is about to use it a great deal. It compares models for speed and tag quality, and with a
configured name each arm of that comparison is a config edit and a restart — which is both slow and a
new way for the configuration to disagree with what is actually loaded.

Ollama already knows the answer. `GET /api/ps` reports what is resident right now.

## Change

Carries out **ADR35**. Five decisions, all settled there:

1. `OllamaHttpClient` resolves the model from `/api/ps` on each call and uses the returned name in
   the request body. The `ollama.model` property and its constructor parameter are removed, and the
   key is deleted from `application.yaml`.
2. The native API root is derived from `ollama.url` by stripping one trailing `/v1`, giving
   `http://localhost:11434/api/ps`. A URL not ending in `/v1` is used as-is. No new config key.
3. When `/api/ps` reports no loaded models, throw `OllamaException` before contacting
   `/chat/completions`, with a message naming the fix.
4. When it reports more than one, use the first and log a WARN naming all of them.
5. `isAvailable()` reports whether a model is loaded, replacing its current `/v1/models` probe, which
   returns true in exactly the situation where every chat call fails.

Resolution happens inside the send path, so it runs inside the call the `ConcurrencyGate` already
serialises and adds no concurrency of its own.

## Acceptance Criteria

- A chat call against a server with one model loaded puts that model's name in the request body,
  with no `ollama.model` anywhere in the configuration or the code
- A chat call against a server with nothing loaded throws `OllamaException`, and no request reaches
  `/chat/completions`
- The exception message names `ollama run` as the fix, so the log is actionable without reading this
  file
- A server with two models loaded produces a call against the first and one WARN naming both
- An unreachable Ollama still produces the existing unreachable-service error, distinct from the
  nothing-loaded error
- `/api/ps` is requested at `http://localhost:11434/api/ps` when `ollama.url` is
  `http://localhost:11434/v1`, and at `<url>/api/ps` when the URL does not end in `/v1`
- `isAvailable()` returns false against a reachable server with nothing loaded
- `gradle build` is green, and `OllamaHttpClientTest` covers each case above against
  `MockRestServiceServer`

## Out of Scope

- A startup probe that warns when nothing is loaded. ADR35 records that the application will fail
  every LLM call after a reboot with no warning until someone runs a model. P2.10 put startup probes
  out of scope and no story has picked them up; this one does not either, because it is production
  code with its own design question — what the application should do about it, not just how to detect
  it
- Changing what a failed classification does. ADR31 makes an `OllamaException` non-fatal, so a
  machine with nothing loaded fills the vault with untagged documents at one ERROR each. That is
  ADR31's deliberate choice and revisiting it alongside this change would make both unreviewable
- Choosing which model to load. [[P2.11]] measures that; this story makes the choice a runtime one
  instead of a configured one
- `response_format: json_schema` and a capped `num_ctx`, both of which
  `design/SPIKE-LOCAL-MODEL-SELECTION.md` argues for. Separate change, separate story
