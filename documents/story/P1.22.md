# Story P1.22 — Restart Endpoint

## Status

READY. Design settled in **ADR40**. No code written.

## Problem

`POST /api/shutdown` stops the application and nothing starts it again. Every change to
`application.yaml` — which is read once, at startup — costs a trip to a terminal: stop the process,
run `bootRun`, wait for it to come up. P1.19 removed that round trip for templates by turning the
Thymeleaf cache off. Configuration still has it.

A process cannot relaunch itself. Once the context closes, the thing that would issue the new launch
is the thing that just died, so the relaunch has to be running outside the JVM before the JVM goes
away.

## Change

A new `POST /api/restart` beside the existing shutdown endpoint, and a PowerShell script it spawns.

**The endpoint**, in this order:

1. Stop the actuator threads inline, the way `/api/shutdown` does, so the response can report how
   many were stopped.
2. Spawn `scripts/restart.ps1` as a detached process, passing this JVM's process id
   (`ProcessHandle.current().pid()`) and the repository root.
3. Answer `202 Accepted` with the actuator count.
4. Call `System.exit` after `shutdown.close-delay-ms`, so the response reaches the caller first.

**The script**, `scripts/restart.ps1`:

1. Wait 30 seconds.
2. If the old process is gone **and** something is listening on 8080, exit silently — the application
   is already back and a second `bootRun` would only fail to bind.
3. Otherwise launch `scripts/build-log.ps1 -Task bootRun`.

ADR40 carries the reasoning, including why `System.exit` is used here when ADR36 rules it out for
shutdown, and what the script's first version deliberately does not handle.

## Design

**ADR40** — `documents/design/ADR40-restart-endpoint.md`. It amends ADR36 on one point: the
no-`System.exit` rule holds for `/api/shutdown` and is set aside for restart, because the successor
needs port 8080 freed at a predictable moment rather than whenever the last non-daemon thread
finishes.

Numbered 40 because ADR38 reserves ADR39 for whatever closes DD-4.

## Acceptance Criteria

- `POST /api/restart` exists and returns `202 Accepted` carrying the number of actuators stopped
- The endpoint is POST only; a GET to `/api/restart` does not restart the application
- The response is received by the caller before the JVM exits
- `scripts/restart.ps1` exists, takes the old process id and the repository root as parameters, and
  waits 30 seconds before doing anything
- With the old process gone and something listening on 8080, the script exits without launching
- With neither condition met, the script launches `bootRun` through `scripts/build-log.ps1`
- The spawned script survives its parent's exit — verified, not assumed
- End to end on this machine: `POST /api/restart`, then within roughly a minute `GET /` answers 200
  again from a process whose id differs from the one that served the request
- `scripts/INDEX.md` carries a row for `restart.ps1`
- `gradle build` green with nothing skipped

## Notes

**The known gap is in the specification, not an oversight.** If the old process is still alive after
30 seconds, the script launches `bootRun` anyway and that launch fails to bind port 8080. The silent
exit is conditioned on the old process being gone *and* a new listener existing, so a process that
refuses to die falls into the "otherwise" branch. Accepted for a first version: the failure is
visible in `@logs/v04-bootRun.log` with the old application still serving, which beats a retry loop
written before anyone has seen the case. Refining the script is expected.

**Two smaller gaps carried**, both in ADR40. The 30-second wait is fixed rather than a poll, so a
restart always costs 30 seconds even when the JVM exits in two. And the endpoint has no
authentication, exactly like `/api/shutdown` — which mattered less when nothing bound the network,
and the application is now reachable from a phone at `192.168.1.166:8080`.

**Testing the detached-process property needs care.** The claim is that a process started by
`ProcessBuilder` outlives the JVM that started it, because on Windows it is not placed in the
parent's job object. That is the assumption the whole design rests on. A unit test can assert the
command line the endpoint would run without spawning anything; the survival property needs the real
end-to-end run in the acceptance criteria above.

**Not in scope:** a supervisor script, restart on crash, and any change to `/api/shutdown`. ADR40
records why the supervisor shape was rejected.
