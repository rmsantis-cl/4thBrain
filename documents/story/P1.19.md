# Story P1.19 — Template Cache Off

## Status

COMPLETED 2026-09-08. One file changed, `application.yaml`, six lines added to the `spring:` block —
`thymeleaf.cache: false` plus a comment carrying the reason, so the next person to read the file finds
the argument without coming here. Nothing else in the file was touched or reordered, so the branch
merges alongside the Phase 2 plans that own the other blocks.

`gradle build` green: 106 tests, 0 failures, 0 skipped.

Verified against a running application on port **8081**, not 8080, which a pre-existing instance was
holding and which was left alone. The check was made the way the cache would defeat if it were still
on: `/admin` was fetched first, so the engine had already parsed and cached that template; a marker
comment was then added to `admin.html` and the file placed into `build/resources/main/templates/`; the
same URL was fetched again with the process untouched and came back carrying the marker. Reverting the
file and fetching a third time removed it again.

One deviation in that loop. The copy into `build/resources/main/templates/` was made directly rather
than by `gradle processResources`, because a second Gradle invocation in this directory blocks on the
project lock the running `bootRun` holds. `processResources` performs a plain copy for these files —
no filtering is configured — so the bytes placed are the bytes Gradle would place, and the property
under test is whether the engine re-reads that file per request, which is what the fetch proved.

Starting the application in a fresh worktree needed `data/` created by hand first. That is
[[BUG-002]], still open and still real.

`/admin/api-docs` returns 404, and did so before this change: `AdminController` maps the API
documentation page at `@GetMapping("/api/docs")` under the `/admin` class mapping, so the URL is
`/admin/api/docs`, which returns 200. The story wrote the path down wrong; the application is fine.
The criterion is recorded as met against the four real URLs.

Rendering was confirmed by status code and response size rather than by a browser, since nothing in
this repository draws a page. The template cache is not a rendering change, so that gap is narrower
here than it was for BUG-003.

## Problem

`spring.thymeleaf.cache` defaults to `true` and nothing in `application.yaml` overrides it, so the
engine parses each template once and serves that parse for the life of the process. A template edit is
invisible until the application is restarted, even after a build has replaced the file on disk in
`build/resources/main/templates/`.

This cost real time during P1.18. The composer was implemented, built and verified, and the running
application kept serving the previous page — the process had been started before the change and would
never re-read the file. The change looked like it had not landed. Diagnosing that is a detour every
time, and it will happen on every template change from here: four pages exist today and P1.12, P1.15
and the admin browser all touch them.

## Change

Set the property in `application.yaml`:

```yaml
spring:
  thymeleaf:
    cache: false
```

It goes in the existing `spring:` block, beside `datasource`, `sql` and `jpa`.

## Design

No ADR. ADR25 already settles the view layer and this is an operational setting underneath it, not a
new decision about how pages are served. What the story does have to record is which of two shapes was
taken, because the obvious objection is real.

**Taken: set it unconditionally.** The cost of `cache: false` is a re-parse of one template per
request. 4thBrain is a single-user application running on the author's desktop, serving four small
static-content pages to one browser. The re-parse is not measurable against a pipeline whose other
stages call a local LLM.

**Rejected: a `dev` profile carrying the property.** Correct in general, and the answer if this were
deployed. It costs an `application-dev.yaml`, a profile to remember to activate, and a second
configuration surface that can drift from the first — machinery that exists to protect a production
deployment this project does not have. `bootRun` with no profile is how the app is started
everywhere it is started.

**What reverses this:** the application being packaged for anything other than the author's own
machine, or a page growing large enough that per-request parsing shows up. Neither is on the roadmap;
if either arrives, the fix is the `dev` profile above, and this story is where to find the reasoning.

## Acceptance Criteria

- `spring.thymeleaf.cache: false` is set in `application.yaml`
- With the application running, an edit to a file in `src/main/resources/templates/` is visible on a
  browser refresh after `gradle build` copies it, with no restart
- The four pages (`/`, `/admin`, `/admin/db`, `/admin/api-docs`) still return 200 and render
- `gradle test` stays green

## Notes

**Verification needs the build, not just the editor.** `bootRun` serves templates from
`build/resources/main/templates/`, not from `src/`. Turning the cache off means the engine re-reads
that copy per request; it does not mean it reads `src/`. So the loop is edit → `gradle build` (or
`processResources`) → refresh. A story that later wants edit-and-refresh with no build step is asking
for `spring.devtools` or a `spring.thymeleaf.prefix` pointed at `src/`, and that is a different change
with its own trade-offs.

**Running a build while the app is up does not work in one directory.** The loop above assumes the
Gradle build and the running application can take turns. They cannot: `bootRun` holds the project
lock for as long as the application runs, so `gradle processResources` from a second shell waits
instead of copying. Either stop the app to rebuild, which gives the restart back and defeats the
point, or place the file into `build/resources/main/templates/` some other way. This is worth knowing
before the next person tries the loop and concludes the cache setting did not work.

`plan-P2.5.md` (`indexer:`/`smartconnections:`). This story touches the `spring:` block, which none of
