# Story P2.8 — Spike: MarkItDown as the Extractor's Converter

## Outcome — closed 2026-09-10 as a decision, without the corpus

**The fixture corpus and every measurement it would produce are waived, not met.** They were never
assembled — running them needs the real document inflow, which is the user's own machine and not
something any agent here can reach — and closing the spike now is a deliberate decision to stop
waiting on them, not a claim that they happened.

What makes that acceptable rather than premature: **ADR38** ("What the census gates, precisely")
narrows exactly what the unrun census would have decided. It gates one thing — which class sits
behind the `MarkdownConverter` interface, `MarkItDownConverter` or a Tika implementation — and
nothing about whether the interface exists, its shape, the failure taxonomy, or how the Extractor
calls it. Story P2.9 already treats the seam as buildable independent of the census for exactly
this reason. Closing P2.8 unblocks that narrow, well-scoped decision; it does not pretend the
broader spike finished.

**ADR28's triggers stay live.** Trigger 1 (PDF-dominated inflow) and trigger 2 (more than a quarter
scanned) can still reverse the stack — replace `MarkItDownConverter` with a Tika implementation
behind the same interface — whenever the census is eventually run. Trigger 3 (subprocess-startup
cost against the Classifier's Ollama call) still wants its number too. None of this is resolved;
it is deferred, on the record, the same way P1.17 deferred its own unmet prototype criterion when
it closed as a decision rather than as a completed spike.

## Why This Spike Exists

Story P2.3 (TextExtractor Real Logic) specifies "PDF → OpenDataLoader, HTML → Turndown, Word → Mammoth". That list came from v03, which ran on Node.js. Turndown and Mammoth are JavaScript libraries and v04 is Java-only, so P2.3 as written cannot be implemented. The extraction stack choice was never made for v04.

## Spike Overview

Evaluate [MarkItDown](https://github.com/microsoft/markitdown) (MIT, Python ≥ 3.10) against Apache Tika. MarkItDown covers PDF, DOCX, PPTX, XLSX, HTML, EPub and produces Markdown for LLM consumption. Compare:

1. **Output quality** against what Classifier needs
2. **Integration options** — how does a Spring Boot JVM call an external Python tool?
3. **Performance** — latency and startup overhead
4. **Failure modes** — corrupt files, encrypted PDFs, scanned PDFs without OCR

Six integration options analyzed in detail in `documents/design/SPIKE-MARKITDOWN.md`:
- CLI subprocess per document
- Persistent Python worker
- HTTP sidecar (FastAPI/Flask)
- markitdown-mcp over MCP
- Embedded Python (GraalPy)
- Apache Tika in-process (comparison arm)

## Timebox

One day. Spike code lives in `spikes/markitdown/` (throwaway, not part of production).

## Acceptance Criteria

- **Fixture corpus:** 15–20 real documents from the actual inflow, including scanned PDF and corrupt file, with converter output committed
- **Output quality:** Per-format results for both candidates (quality, latency, failure behavior, Windows UTF-8 handling, install footprint)
- **Decision:** Written recommendation naming one stack and one integration option, backed by measurements
- **ADR:** Decision recorded in `documents/design/ADRS.md`
- **P2.3 rewritten:** Story updated to name the chosen stack

## Scope

- No production code lands under P2.8
- Image description and audio transcription out of scope
- Azure Document Intelligence out of scope
- ZIP handling stays in Java per P1.8

## Not Blocked by Phase 1

The spike runs against files on disk and needs neither a booting application nor the actuator chain.

## Key Risks

- **Scanned PDFs:** Local path has no OCR; both MarkItDown and Tika return little from image-only PDFs
- **Second Python runtime:** On Windows/WSL2 with Ollama and Obsidian already running, Python adds operational burden
- **Upstream churn:** MarkItDown is young; pin version and treat startup probe as version check
- **Scope creep:** Image/audio tempting but belong to Classifier's budget, not Extractor's

**Not done, and waived rather than met — see Outcome.**

- *Fixture corpus.* No 15–20 document corpus was assembled and no converter output is committed.
- *Measurements.* No per-file quality verdict, no latency, no failure behaviour on a real encrypted
  or scanned PDF, no install footprint on the target machine. The ADR was taken on the argument, and
  says so in its own Context section.

The research arm was explicit that the decision hinges on a number nobody has: **the format mix of
the real inflow.** On PDF, MarkItDown and Tika are both flat text extractors, so MarkItDown's
advantage evaporates and the Python runtime is bought for nothing; on DOCX, PPTX, XLSX and HTML it
earns its keep. That is a count, not a judgement, and it takes ten minutes:

```
Get-ChildItem -Recurse -File <inflow-root> |
  Group-Object Extension |
  Select-Object Name, Count, @{n='TotalMB';e={[math]::Round(($_.Group|Measure-Object Length -Sum).Sum/1MB,1)}} |
  Sort-Object Count -Descending
```

Then split digital PDFs from scanned by counting extracted characters per page; under about 100 means
no text layer. More than a quarter scanned and the real output of this spike is an OCR decision, not
a converter choice.

**Whoever runs this later** — the census was never a precondition for P2.9's own work (see Outcome),
only for whether `MarkItDownConverter` is the right class behind the seam. Running it can still
reverse that one piece under ADR28's triggers 1 and 2.
