# Story P1.13 — Ingest-by-Value Endpoint (Text and URL)

## Problem

Two of the three ingestion endpoints do nothing, and their tests assert a design that was removed.

`IngestionController.submitText` and `submitUrl` log `Not implemented` and return `{"not":"implemented"}`. The real body of `submitText` is present but commented out, and it calls `databaseService.createDocument("text", text)` — passing a literal as what was then the path column, which P1.8 has since removed.

All 23 tests in `IngestionControllerTest` fail. They assert `$.jobId`, mock `databaseService.createDocument(...)`, and verify `coordinator.startChain(1L)` — the Job-based design that was deliberately removed.

Separately, `/text` and `/url` are two endpoints for one operation — putting something into the vault by value rather than by file. That duplicates work the composer (P1.17) already does: it detects, client-side, whether what the user typed is a URL or a note, in order to decide which button lights up. Wiring that same detection to a choice of *path* just repeats it on the way to the server. ADR26 settles this: one endpoint, and the UI's own detection decides which field of the body to populate.

## Change

Per ADR26 (`documents/design/ADRS.md`):

1. Replace `submitText` and `submitUrl` with a single handler, `POST /api/ingest/capture`, taking a JSON body with either a `url` key or a `text` key set — never both. The controller dispatches on which key is present.
2. `url` present: create a Document with `source_url` set, `content` empty, no copy row, then start the chain so `Clipper` fetches it. This also requires `Ingestor.isUrl` and `Clipper.doTheThing` to read `sourceUrl` instead of `content` (ADR26 decision 5) — without it the document matches neither `isUrl` nor `isTextContent` and stops silently at `ingested`.
3. `text` present: create a Document with `content` set to the posted text and no copy row, since nothing is on disk, then start the chain.
4. `/api/ingest/file` is unchanged — a multipart upload has nothing in common with a JSON body, so it stays a separate endpoint. The UI decides which of the three (file, url, text) applies; the server only decides between url and text within `/capture`.
5. Rewrite the tests against the current contract: `id` rather than `jobId`, proper service calls, and the working entry point from P1.11.
6. One response shape across all three ingest endpoints, per ADR26: `{ "id": ..., "status": ..., "message": ... }`.

## Acceptance Criteria

- `POST /api/ingest/capture` with a `text` body creates a Document, starts the pipeline, and returns the agreed shape
- `POST /api/ingest/capture` with a `url` body produces a document with `source_url` set and no `document_copy` row, and reaches `Clipper`
- A body carrying neither `url` nor `text` (or both) is rejected rather than silently guessed at
- `/api/ingest/text` and `/api/ingest/url` no longer exist; nothing in `src/main` or `index.html` posts to them
- `gradle test` passes, with no test asserting `jobId`, `/api/ingest/text`, or `/api/ingest/url`

## Status: Implemented 2026-09-07

Implemented via `plan-11-13-17.md`. `POST /api/ingest/capture` replaces `submitText`/`submitUrl`,
dispatching on whichever of a `url`/`text` body key is present (rejecting neither-or-both with a 400);
`Ingestor.isUrl` and `Clipper.doTheThing` read `sourceUrl` instead of `content`; `/api/ingest/file` is
unchanged apart from the shared `{ id, status, message }` response shape; `index.html`'s text and URL
panels post to `/capture`.

This landed ahead of P1.17's spike actually running — `plan-11-13-17.md` argued explicitly that P1.13's
endpoint contract only needs the four contract-bearing answers from the spike's output table (routing
UI vs. endpoint shape), not the routing decision itself (mode toggle vs. two buttons vs. auto-detect),
and ADR26 already settles the one contract-bearing answer that mattered here (one endpoint, keyed on
body content). P1.17 and ADR27 remain open; P1.18 (the composer) still cannot start until ADR27 is
written.

Verified by `gradle build` and `gradle test` (`BUILD SUCCESSFUL`); `IngestionControllerTest` rewritten
against `/capture`, with explicit cases asserting `/api/ingest/text` and `/api/ingest/url` return 404.
