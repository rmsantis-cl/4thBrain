# Story P1.18 — The Unified Composer

## Status

**COMPLETED 2026-09-07.** Implemented from `documents/plan-P1.18.md` v1.1, which had itself been
revised against `documents/review-plan-p1.18.md`. One file changed: `index.html`, 376 insertions and
189 deletions.

Verified against a running application on port 8081 (port 8080 was held by a pre-existing instance,
which was left alone):

- `gradle build` green, tests included.
- `GET /` returns 200 and renders. All seven composer element ids are present; `panel-add-file`,
  `panel-add-text`, `panel-add-url`, `panel-chat-llama`, `chat-window`, `chat-message`,
  `chat-input-row`, `result-msg`, `llamaHistory` and `uploadFile` are all gone. Four nav items.
- ADR25 held: no `th:inline` anywhere, and every `${...}` template literal survives rendering intact,
  including the ones the rewrite added.
- All four endpoints the composer calls answer with the shapes the feed reads.
  `/api/ingest/capture` returns `{ id, status, message }` for both keys; `/api/ingest/file` returns
  those three plus `fileName` and `mimeType`; a body setting neither or both keys returns 400 with
  `{ message }` and no `id`; `/api/chat/llama` returns `{ reply }`, still the echo stub (DD-5).
- A URL submission produced a document with `source_url` set and no `document_copy` row, which the
  Clipper then fetched into a child document. A text submission produced `content` set and
  `source_url` null, so ADR27's `SEND`-on-a-bare-URL override behaves as specified. Non-ASCII text
  round-tripped through capture and into the database unchanged.

**Outstanding, and it needs a person.** ADR27's own reopening question — whether the four-control row
feels dense in use, and whether `ASK` gets pressed by mistake — cannot be answered by this pass. The
story records it as the evaluation the spike skipped, and it stays open until someone has used the
screen for a while. The optional `Ctrl+Enter` accelerator the plan added past ADR27 is part of what
gets evaluated, not a settled feature.

Two things found during implementation that are recorded rather than fixed here, because both belong
to other stories:

- A captured text document has no file on disk and no copy row, so the Indexer has nothing to move
  and the document stops before reaching the vault. Owned by `plan-P2.2.md` (materialise upstream)
  and `plan-P2.5.md` (fallback at the Indexer).
- The `Clipper` leaves its child document at status `New` when it hands it back to the Ingestor, so a
  clipped page can sit unprocessed. Not P1.18's, and not currently owned by any story.

## Problem

P1.11, P1.17 and P1.13 each deliver a piece of "one entry point for everything the user puts into the
vault", and none of them lands the piece the user actually sees. P1.11 makes the pipeline callable.
P1.17 is a spike — its own scope forbids production code — and only produces a routing decision.
P1.13 makes `/api/ingest/capture` (text and URL) and `/api/ingest/file` work behind whatever front end
is already there, which today is still three separate panels (Add File, Add Text, Add URL) plus a
fourth for Chat.

The composer that makes those feel like one entry point does not exist yet. This story is that
follow-on, named as an exit criterion of P1.17's own acceptance criteria ("Follow-on story:
Implementation storied separately, blocked by P1.13").

## Change

1. Build ADR27's composer into `index.html`: one rounded container holding a text area with its
   controls inside it, `[+]` bottom-left and `ASK` `URL` `SEND` bottom-right, replacing the Add File,
   Add Text and Add URL panels. **Chat folds in too** — `ASK` posts to `/api/chat/llama` and the reply
   lands in the same feed as capture receipts, so the Chat with Llama panel goes as well and the nav
   drops from six items to four.
2. Wire the composer to the endpoints P1.13 built: `URL` posts `{ "url": ... }` and `SEND` posts
   `{ "text": ... }`, both to `POST /api/ingest/capture`; an attached file still posts multipart to
   `POST /api/ingest/file`. Which button was pressed picks `url` vs `text` — the server does not
   re-derive it (ADR26).
3. Implement ADR27's URL rule: the `URL` button is disabled unless the whole trimmed input is a single
   `http`/`https` URL with nothing around it (no whitespace, parses under `new URL()`, protocol is
   `http:` or `https:`). Detection only enables the button. Pressing `SEND` on a bare URL stores it as
   text, which is the user's override and needs no separate control.
4. Carry over ADR27's composition answers: text plus an attached file is two submissions and two
   Documents (file to `/api/ingest/file`, text to `/api/ingest/capture`); several files are one
   Document each; **no tags field** (deferred, DD-3); nothing to reset, because there is no mode.
5. Apply the response shape from ADR26 (`{ id, status, message }`) to the receipt feed. **Do not build
   per-document status** — no endpoint reports it and no story owns one (DD-2), so a receipt shows what
   the server returned at submission and does not update.
6. Remove the four superseded panels — Add File, Add Text, Add URL and Chat with Llama — and their
   now-dead JavaScript from `index.html` once the composer covers their function. Keep ADR25's
   constraints: the page stays in `templates/`, no bundler, no framework, and no
   `th:inline="javascript"` is added to any script block using template literals.

## Acceptance Criteria

- `index.html` presents one composer for file, text and URL capture and for asking the model; the four
  panels it replaces are gone, along with any JavaScript that only served them
- A typed URL, a typed note, and an attached file each reach the vault through the endpoint P1.13
  built for that input, with no client-side guess duplicated server-side
- `ASK` reaches `/api/chat/llama` and its reply appears in the same feed as capture receipts
- The `URL` button is enabled for `https://example.com/article` and disabled for
  `see https://example.com/article — worth reading`, for `example.com/article`, and for two URLs on two
  lines; `SEND` on a bare URL produces a text Document
- The receipt feed reflects the response shape from ADR26 for every submission
- Manual smoke test: all three input types submitted through the composer against a running app, each
  reaching the pipeline

All six are met. The URL truth table and the keyboard behaviour are browser-side and were verified by
reading the rendered page and the rule's implementation rather than by driving a browser — there is no
browser harness in the build, which the plan states and P3.4 owns.

## Dependencies

Both cleared. **P1.13** built `/api/ingest/capture`, and **P1.17** produced ADR27, which this story
implements.

ADR27 was taken without a prototype, so this story is the first time the design is used. Treat the
first run of the composer as the evaluation the spike did not do: if the four-control row feels dense,
or `ASK` gets pressed by mistake, that is the evidence ADR27 says would reopen the decision.
