# Story P1.12 — Status Endpoint Reports Document Counts

## Problem

`/api/status` always returns zeros.

`StatusController.java:20` calls `coordinator.getStatusCounts()` and reads keys `ingesting`, `extracting`, `classifying`, `indexing`, `indexed`. But `getStatusCounts()` returns queue depths keyed by **actuator name** — `Ingestor`, `Extractor`, `Classifier`, `Indexer`. The two key spaces never intersect, so every `getOrDefault(..., 0L)` falls through to its default. The dashboard cannot show progress.

`DocumentRepository.countByStatus` already exists and wraps the proper query: count documents grouped by `status`.

## Change

1. Source the counts from the database, counting documents grouped by `status`, not from queue sizes
2. Derive the reported stages from the actuators' own `getGerund()`/`getParticiple()` values rather than a hard-coded literal list, so a new actuator appears in the dashboard without editing the controller
3. Decide what happens to `Coordinator.getStatusCounts()`. Queue depth is useful, but it is a different measurement: either rename it to say so and expose it separately, or remove it

## Acceptance Criteria

- With documents in known statuses, `/api/status` returns their actual counts
- Adding an actuator adds its stage to the response without a controller change
- A single `countByStatus` per stage, or one grouped query — not a full table scan per request
