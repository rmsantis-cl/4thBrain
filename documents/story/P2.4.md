# Story P2.4 — Classifier Real Logic

## Status

**COMPLETED 2026-09-08.** Implemented from `documents/plan-P2.4.md` by an agent in its own worktree,
merged into `v04` last of three. `Classifier.doTheThing` has a real body: build a prompt, call the
model through `OllamaClient`, extract the first balanced JSON object from the reply, normalise, write
`document.topic` and `document_tag` rows, route to `Indexer`. New `classifier:` config block, 33 new
tests (24 parsing/normalisation, 9 behaviour). `gradle build` green.

**The design gate produced ADR31**, currently at
`documents/design/ADR31-classification-contract.md` — standalone, because three agents could not all
append to `ADRS.md` concurrently. **It still has to be folded into `documents/design/ADRS.md`.**

**ADR31 closes DD-3.** Tags come from the Classifier. Manual tagging stays possible and unbuilt, with
`/api/ingest/file`'s existing `tags` parameter as the seam. The `#tag`-is-a-Markdown-heading trap DD-3
named does not fire here only because tags arrive as JSON array elements rather than inline tokens —
recorded explicitly, so a later inline-tagging story knows it inherits the trap intact.

### One acceptance criterion is re-mapped, not met as written

**"Classification and DocumentTag records created correctly."** There is no `classification` table and
none was added: `schema.sql` is shared, and a migration from one of four concurrent branches is the
worst place to put one. The result lives in `document.topic` plus `document_tag` rows, which is what
the story's other requirements ask for anyway. The raw model reply is logged at DEBUG, not persisted;
a later story that wants it kept for prompt tuning can add the table with its own schema change.

### Two decisions worth keeping

- **A parse failure is not a pipeline failure.** An unreadable reply logs at WARN, leaves the topic
  null, writes no tags, and still returns `"Indexer"`. An unclassified document in the vault is worth
  more than a document stuck outside it — and the Classifier has no way to record a failure anyway
  (DD-4). This is deliberately the opposite of ADR28's choice for conversion failures, where a failure
  leaves nothing to index at all.
- **The parser tracks brace depth rather than using a regex.** A lazy pattern returns a prefix that is
  *still valid JSON* with the tags missing, which is worse than a clean failure.

### Departure from the plan

`OllamaClient` is injected `@Autowired(required = false)`. Without it the branch could not start a
context at all, because no implementation was on its classpath while P2.1 was unmerged, and that took
`ActuatorManagerTest` and `CoordinatorTest` down with it. Finding no client, the Classifier logs WARN
and routes on — the behaviour ADR31's D4 already specifies. **Now that P2.1 is merged this can be
tightened to a required injection**, and should be, so a missing client fails at startup rather than
silently producing unclassified documents.

**Outstanding: classification has never run against a real model.** Every test uses a hand-written
fake `OllamaClient`. The agent was instructed not to start the application or make live calls, so plan
verifications 3 to 6 are unrun, and P2.10's contradictory status means it is not even confirmed that
anything answers on `localhost:11434`.

## Overview

Classifier calls OllamaClient with document content and a prompt, parses the LLM response for tags and topic, creates Classification and DocumentTag records, updates Document metadata, and routes to Indexer.

## Implementation Requirements

- Call OllamaClient with formatted prompt including document content
- Parse LLM response to extract tags and topic information
- Create Classification record linking document to response
- Create DocumentTag records for each parsed tag
- Update Document.topic field with classification result
- Handle parsing errors and malformed responses
- Route to Indexer via Coordinator

## Configuration

- Prompt template for LLM classification (configurable in application.yaml)
- Concurrency gated by ConcurrencyGate from P2.1
- Timeout enforcement for LLM calls

## Acceptance Criteria

- LLM classification produces valid tags and topic
- Classification and DocumentTag records created correctly
- Document status updates to classified stage
- Messages route properly to Indexer
- Parsing errors logged and handled gracefully
