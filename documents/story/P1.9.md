# Story P1.9 — Actuator Instantiation & Registration

## Problem

Every actuator is built twice, and startup dies on the second one.

`Ingestor`, `Extractor`, `Classifier`, `Indexer` and `Clipper` each carry `@Component`, so component scan builds one. `ActuatorThreadConfig` also declares `@Bean @Scope("prototype")` factories for four of them plus array beans that call `factory.getObject()`, so it builds another. Two instances of the same class then reach `Coordinator.register()`:

```java
if (!registry.containsKey(a.getClass())) {   // guard is keyed by CLASS
    registry.put(a.getClass(), new ArrayList<>());
    actuator.put(a.getName(), new ArrayList<>());   // but this map is keyed by NAME
}
registry.get(a.getClass()).add(a);
actuator.get(a.getName()).add(a);   // null on the second instance -> NPE
```

The second instance takes the guard's false branch, so no list is created under its name, and `actuator.get(...)` returns null. The NPE propagates, and the context aborts.

### Subsidiary Defects

Three further defects sit underneath:

- **Registration runs before naming.** `Actuator.java:32` calls `Coordinator.register(this)`; `:34` calls `setName(name)`. At registration the object carries Thread's generated name, so the routing map is keyed `Thread-7` rather than `Ingestor`. `Actuator.run()` routes via `Coordinator.get(n)` where `n` is a class simple name, so every lookup would miss.
- **The thread is started twice.** `Actuator.java:40` calls `start()` in the constructor, and `ActuatorThreadConfig` calls `start()` again. The second call throws `IllegalThreadStateException`.
- **The thread runs before injection.** Starting inside the constructor puts the loop live before Spring has populated any `@Autowired` field. `Actuator.service` is worse than racy — it carries no annotation at all, so `DocumentService` is never injected.

## Design

See `documents/design/STARTUP-SEQUENCE.md` for the detailed initialization order and sequence diagram.

1. `ActuatorThreadConfig` becomes the sole creator. Drop `@Component` from all five actuator classes.
2. Create a new `ActuatorManager` bean:
   - `@PostConstruct` → create all instances via `ObjectFactory`, inject, name as `<Type>-<index>`, register all with Coordinator
   - `ApplicationReadyEvent` listener → start every thread, exactly once, only after the context is fully refreshed
   - `@PreDestroy` → `shutdown()` each actuator (clear `running`, interrupt, join)
3. `Actuator`'s constructor sets up name, logger and flags only: remove `Coordinator.register(this)` and `start()`
4. `Coordinator.register()` keys the routing map on `a.getClass().getSimpleName()`, not `a.getName()`. Seed both maps with `computeIfAbsent`.
5. `Actuator.service` gains `@Autowired`, or moves to setter injection
6. `Extractor` and `Clipper` autowire an `Ingestor` field. Once `Ingestor` is a prototype, injecting it mints a fresh unregistered actuator. Both should reach it through `Coordinator.get("Ingestor")`.

Several instances of one class stay correct because they share a static queue, so `Coordinator.get(name)` returning the first registered instance still enqueues work any of them can pick up.

### Configuration Changes

- Add `actuators.threads.clipper: 1` to application.yaml
- Keep or remove `actuators.threads.briefing: 1` with a comment

## Acceptance Criteria

- `actuators.threads.<name>: N` produces exactly N instances of that class and no more
- The application logs `Started FourthBrainApplication`
- `Coordinator.get(...)` returns a registered instance for all five actuator types
- No `IllegalThreadStateException` in the startup log
- Every actuator holds a non-null `DocumentService` before its thread processes a message
- `shutdown()` stops an actuator's thread within a bounded time

## Out of Scope

Tracked as P1.10: the run loop's busy spin, and the `running` flag having no way to be cleared outside `@PreDestroy`. P1.10 was in fact implemented in the same pass, and the two were verified together.

## Status

Implemented and verified 2026-09-06. `ActuatorManager` is the sole lifecycle owner, in three phases: `@PostConstruct` creates every instance through its `ObjectFactory` and names it, then registers all of them; `ApplicationReadyEvent` starts every thread once; `@PreDestroy` shuts them down. `@Component` is off all five actuator classes, `ActuatorThreadConfig` keeps only the prototype `@Bean` factories, and `Actuator`'s constructor does no lifecycle work. The Coordinator registry is a `ConcurrentHashMap` of `CopyOnWriteArrayList` keyed by class simple name, since ActuatorManager writes it on the main thread and every actuator thread reads it on each routing hop.

Verified by `gradlew bootRun` against a fresh database — `Created 1 <Type> instance(s)` for all five types, `Registered 5 actuator instance(s)`, `Started 5 actuator thread(s)`, `Started FourthBrainApplication`, no `IllegalThreadStateException` — and by `ActuatorManagerTest`, which asserts against `Coordinator.instancesOf(...)` rather than log lines: `actuators.threads.ingestor=2` yields exactly two Ingestors, all five names resolve through `Coordinator.get`, every instance holds an injected `DocumentService`, and instances of one class share a queue. Context close logs `Thread exiting.` once per actuator, then `Shut down N actuator thread(s)`.

Three defects were found in the implementation while verifying it, and fixed: the registry was published unsafely (a plain `HashMap`, written under a lock and read without one); `run()` dereferenced the result of `Coordinator.get(n)` with no null check, so an unregistered name would NPE inside the loop; and the `InterruptedException` handler re-set the interrupt flag without leaving the loop, which would busy-spin on any interrupt other than shutdown's. `build.gradle` also declared `sourceCompatibility = '17'` while `Coordinator` used `List.getFirst()`, a Java 21 API — it compiled only because Gradle sets `-source`/`-target` without `--release`, and the declared level is now 21.
