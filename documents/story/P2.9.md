# Story P2.9 — MarkdownConverter seam and implementation

> The stack is settled: **ADR28** chooses MarkItDown invoked as a subprocess. This story carries it
> out. Section "Decision" below is the story's own reasoning, written before the ADR and reaching
> the same answer independently; the ADR is the record of the decision, and where the two differ the
> ADR wins. The ADR was taken on the argument rather than on P2.8's corpus measurements, which have
> not been run — so the placeholders in "Contingent on P2.8's measurements" at the end of this file
> are still open, and ADR28's triggers 1 and 2 can still reverse the stack. Run the format census
> before writing code.

## Problem

`Extractor.java` unzips ZIP archives and creates a child Document per member (`Extractor.java:99-142`). That is all it does. Nothing anywhere in `src/main` turns a PDF, a DOCX, a PPTX, an XLSX, an EPub or a saved HTML page into Markdown. The Classifier is downstream of a step that does not exist yet.

P2.3 was written against v03's Node stack — Turndown, Mammoth, OpenDataLoader — none of which can run in this build. P2.8 measures the two candidate replacements. Neither P2.8 nor P2.3 delivers the code: P2.8 is a throwaway spike under `spikes/`, and P2.3 is the actuator rewrite that archives originals, calls the converter and routes to the Classifier.

The missing piece between them is the converter itself: an interface the Extractor can depend on, one implementation behind it, its configuration, a startup check that fails loudly rather than at the first document, and failure semantics precise enough that a document can never disappear into an in-progress status with no thread coming back for it.

## Decision

P2.9 delivers `MarkdownConverter` and one implementation, `MarkItDownConverter`, which invokes the pinned `markitdown` CLI as a child process per document.

The reasoning, independent of the brief's going-in position:

**A child process is the only place a hard timeout actually exists.** This pipeline is driven by `Document.status`. A document that stalls is invisible — no queue entry, no error row, nothing to sweep. An in-process parser that enters a tight loop on a malformed PDF cannot be stopped from Java. `Thread.interrupt()` does nothing to a thread inside PDFBox, and `Thread.stop` is gone. The only reliable remedy in-process is to have no remedy. `Process.destroyForcibly()` is a remedy. The brief lists this under "crash isolation", which understates it — a segfault is loud and rare, an uninterruptible parse is quiet and permanent, and the quiet one is the one that breaks a status-driven pipeline. Tika's own answer to this problem is `ForkParser` or `tika-server`, both of which put a process boundary back. Once a process boundary is required either way, the choice narrows to which runtime sits on the far side of it.

**Memory is the same argument.** A 100 MB input parsed in the JVM competes with the pipeline for heap. In a child process it competes with nothing that matters and dies alone.

**The Java code stays small.** MarkItDown covers the whole format list through one command line. Tika emits text or XHTML, so the Markdown step is a second component to write, tune per format and own. That is code in this repository, with this repository's bug reports.

**No new compile dependency.** The build has no document-parsing or AI dependency today. The subprocess implementation needs the JDK and nothing else. Tika brings PDFBox, POI and their transitive graph into a single-user desktop application, along with the advisory traffic that follows those two.

The cost is a Python runtime the user has to install and keep. That is real and it is theirs, not the code's. It is paid once, in a project-local venv named by absolute path in `application.yaml`.

**Options rejected without needing a measurement.** GraalPy gives up process isolation to save a spawn, which inverts the reason for having a boundary; MarkItDown's dependency graph (`pandas`, `lxml`, `onnxruntime` under `magika`) is the worst case for it. `markitdown-mcp` settles the "how does Java speak MCP" question as a side effect of picking a document converter, which is the wrong order — P2.5 deserves that decision on its own terms, and until it has one, adding Spring AI or the MCP SDK to this build buys a JSON-RPC envelope around a whole document body. A persistent stdin/stdout worker means writing, framing and supervising a protocol that does not exist upstream, to save a cost nobody has measured. The HTTP sidecar is the right answer at higher concurrency and the wrong answer for one user with no supervisor, one Extractor thread and a Classifier gated to a single Ollama call; the seam this story delivers is what makes moving there later a configuration change.

### Where this departs from the brief

- The brief's implicit case for MarkItDown is that it targets LLM consumption where Tika targets search indexing. That holds for DOCX, PPTX, XLSX and EPub, where the source carries heading styles, slide titles and cell grids that `mammoth`, `python-pptx` and `pandas` can render as Markdown headings and tables. It does not hold for PDF. MarkItDown's local PDF path is `pdfminer.six` and `pdfplumber`, which return flat text with no heading structure — much the same shape Tika's PDFBox path returns. If the corpus is mostly digital-text PDF, expect near-parity on quality and let install footprint decide. Say so in the ADR rather than letting "built for LLMs" carry the argument.
- The interface in the brief has one method. Two more belong on it. `supports(String)` keeps the format skip-list next to the component that knows the formats, instead of in the actuator where it will drift. `probe()` lets the startup check be implementation-specific without the caller knowing what is being probed.
- Do not rely on `-x/--extension` with a file argument. That flag is documented for stdin input, and the Clipper writes HTML into files whose suffix may not be `.html`. Stage a copy with the correct suffix instead. That also removes filename encoding from the picture, since the staged name is generated ASCII.
- A `--version` probe checks that a binary exists. It does not check that the `[pdf,docx,...]` extras installed, that `-o` can write, or that non-ASCII survives the channel on Windows. Probe with a real conversion of a tiny bundled fixture, and check the version too.
- The brief suggests carrying a Tika implementation in production as a second class behind the same interface for comparison. Do not. One implementation on the classpath. A second one that was not chosen is dead code dragging PDFBox and POI along behind it. The comparison lives in `spikes/markitdown/`.

## Design

### Package layout

New package `com.fourthbrain.convert`:

| Class | Role |
| :---- | :---- |
| `MarkdownConverter` | the interface; the only type `Extractor` sees |
| `MarkItDownConverter` | `@Component`, `@ConditionalOnProperty(name="fourthbrain.converter.implementation", havingValue="markitdown", matchIfMissing=true)` |
| `ConverterProperties` | `@ConfigurationProperties("fourthbrain.converter")` |
| `ConversionException` | checked; carries `Reason` and detail |
| `ProbeResult` | record `(boolean available, String version, String detail)` |
| `ProcessRunner` / `DefaultProcessRunner` | the ProcessBuilder call, extracted so tests can fake it |

### Interface

```java
package com.fourthbrain.convert;

public interface MarkdownConverter {

    /** Convert source to Markdown. Never returns null, never returns blank. */
    String convert(Path source, String extensionHint) throws ConversionException;

    /** True if this converter will attempt extensionHint (no leading dot, case-insensitive). */
    boolean supports(String extensionHint);

    /** Cheap enough to call at startup, expensive enough to be worth calling. */
    ProbeResult probe();
}
```

```java
public class ConversionException extends Exception {
    public enum Reason {
        UNAVAILABLE, UNSUPPORTED_FORMAT, TOO_LARGE,
        TIMEOUT, CONVERTER_FAILED, EMPTY_RESULT,
        OUTPUT_TOO_LARGE, IO_ERROR
    }
    private final Reason reason;
    private final String detail;   // safe to persist; stderr excerpt, capped
}
```

The converter does not touch the database, the vault or `Document`. It takes a path, returns a string or throws. Provenance for front matter (converter name and version) comes from `probe()`, which P2.3 can call once and cache.

### Configuration

Under a new `fourthbrain.converter` key in `application.yaml`, alongside the existing actuator thread-count settings:

```yaml
fourthbrain:
  converter:
    implementation: markitdown
    fail-fast: true                 # abort boot if the probe fails
    supported-extensions: [pdf, docx, doc, pptx, xlsx, xls, html, htm, epub, msg, csv, json, xml]
    passthrough-extensions: [md, markdown, txt, text]
    min-output-chars: 1
    max-input-bytes: 104857600      # 100 MiB, provisional — see P2.8
    max-output-bytes: 33554432      # 32 MiB
    max-concurrent-processes: 2
    markitdown:
      executable: ""                # absolute path to the venv's markitdown
      python: ""                    # alternative: absolute python, invoked as -m markitdown
      expected-version: ""          # pin after P2.8; empty disables the check
      version-check: warn           # off | warn | fail
      timeout: 120s                 # provisional — see P2.8
      work-dir: ""                  # defaults to java.io.tmpdir/4thbrain-convert
      env:
        PYTHONUTF8: "1"
        PYTHONIOENCODING: "utf-8"
```

`executable` and `python` are absolute paths. Neither falls back to a bare `markitdown` on `PATH`; if both are empty the probe fails. Exactly one may be set.

### The conversion path

1. Normalise `extensionHint` — strip a leading dot, lowercase. If it is `zip`, throw `UNSUPPORTED_FORMAT` unconditionally, whatever the configuration says. ZIP expansion belongs to `Extractor` under P1.8's one-Document-per-member model, and MarkItDown would flatten an archive into one concatenated document. If the hint is in `passthrough-extensions` or absent from `supported-extensions`, throw `UNSUPPORTED_FORMAT`.
2. If the probe result is unavailable, throw `UNAVAILABLE` without spawning anything.
3. `Files.size(source) > max-input-bytes` → `TOO_LARGE`, no spawn.
4. `tryAcquire` a permit from a `Semaphore(max-concurrent-processes)` bounded by the configured timeout. Failure to acquire is a `TIMEOUT` with detail naming the permit, not a separate reason — the caller's handling is identical.
5. Create a per-call directory under `work-dir` and stage the source into it as `in-<uuid>.<ext>` by copy. The generated name is ASCII, so no part of the command line depends on how the original filename encodes. The output path is `out-<uuid>.md`, stderr goes to `err-<uuid>.txt`.
6. Build the argument list — never a shell string, so a filename containing `&` or a quote is a non-event:
   `[<executable>, <stagedPath>, "-o", <outPath>]`, or `[<python>, "-m", "markitdown", ...]`. No `-p`: plugins stay off. No `--keep-data-uris`: base64 image payloads are not text the Classifier can use.
7. `redirectInput(Redirect.from(<empty file>))`, `redirectOutput(Redirect.DISCARD)`, `redirectError(Redirect.to(errFile))`. No pipe is left for the parent to drain, which is the failure mode that turns this option into a hang.
8. Environment gets `PYTHONUTF8` and `PYTHONIOENCODING` from config, merged over the inherited environment.
9. `waitFor(timeout)`. On expiry: `destroy()` each of `process.descendants()` then the process, wait 2 s, `destroyForcibly()` anything left, wait again, throw `TIMEOUT`. The child is dead before `convert` returns; nothing holds the staged file afterwards.
10. Non-zero exit → read up to 8 KiB of `errFile`, keep the first and last lines, throw `CONVERTER_FAILED` with that as detail.
11. Exit 0 but output missing, or larger than `max-output-bytes` → `OUTPUT_TOO_LARGE` for the latter, `CONVERTER_FAILED` for the former.
12. Read the output as UTF-8 strictly. On `MalformedInputException`, re-read with a replacing decoder, log at WARN with the path, and keep going — a document with three replacement characters beats no document. Strip a BOM, normalise `\r\n` to `\n`.
13. Fewer than `min-output-chars` non-whitespace characters → `EMPTY_RESULT`. This is the scanned-PDF case and it must not pass: empty Markdown would be classified as nothing and indexed as noise.
14. `finally`: delete the per-call directory, release the permit. Deletion failure is logged, not thrown.

### The startup probe

`@PostConstruct` on `MarkItDownConverter`, so the bean is either usable or the context is broken before any actuator thread starts.

1. Run `<executable> --version` with a 10 s timeout. Record the version string.
2. If `expected-version` is set and does not match: `version-check: fail` throws, `warn` logs at WARN, `off` skips. The brief is right that this should be a version check and not just a liveness check — MarkItDown's CLI surface has moved before.
3. Write `probe-<uuid>.html` containing a heading and a non-ASCII line (`<h1>Prüfung — ok</h1>`), convert it, and assert the returned Markdown contains `Prüfung` and `—`. That covers the executable, the `-o` write path, the extras install and the Windows encoding trap in one go.
4. Store the outcome in a `volatile ProbeResult`.
5. On failure with `fail-fast: true`, throw `IllegalStateException` whose message contains the full command line, the exit code, the stderr excerpt and the venv install command. With `fail-fast: false`, log at ERROR and leave the converter unavailable; every `convert` then throws `UNAVAILABLE` immediately.

### What happens to the Document when conversion fails

The converter is deliberately persistence-free, so `Reason` is the entire interface between it and the actuator. The following mapping is a binding contract on P2.3, fixed here so that story has nothing left to invent. Confirm the constant names against the existing `Document` status enum and reuse an equivalent if one is already there; add what is missing, with a `statusReason` column if the entity has no field able to hold the detail string.

| Reason | Status | Why that status |
| :---- | :---- | :---- |
| `UNSUPPORTED_FORMAT` | `EXTRACTION_UNSUPPORTED` | queryable backlog of "formats to add a converter for" |
| `EMPTY_RESULT` | `EXTRACTION_EMPTY` | queryable backlog for a later OCR story; distinct on purpose |
| `TIMEOUT`, `CONVERTER_FAILED`, `TOO_LARGE`, `OUTPUT_TOO_LARGE`, `IO_ERROR`, `UNAVAILABLE` | `EXTRACTION_FAILED` | retry candidates once a human has looked |

Three rules that follow, and that the acceptance criteria check:

- No failure path leaves a document in an in-progress status. The actuator's `catch (ConversionException)` writes the terminal status and the reason detail in the same transaction, before it takes the next queue item.
- `catch` sits inside the actuator's loop, not around the thread body. One bad document does not end the thread, and the thread does not need restarting.
- Nothing else in the pipeline moves a document out of `EXTRACTION_*` on its own. These are terminal until something deliberate — a retry command, an OCR story — moves them.

### Thread safety and tests

`MarkItDownConverter` holds only configuration, the probe result and the semaphore. Every call has its own directory and its own generated filenames, so the class is reentrant across however many Extractor threads the configuration asks for.

`ProcessRunner` is a functional interface over "run this command with this environment and this timeout, give me exit code or an expiry signal". `DefaultProcessRunner` is the ProcessBuilder implementation. Tests substitute a fake that can produce a non-zero exit with canned stderr, an expiry, a missing output file, an output file with malformed UTF-8, an output file of whitespace, and an oversized output file. That covers steps 9 to 13 with no Python installed and no OS branching.

Command construction is a package-private method tested directly against paths containing spaces and shell metacharacters.

One live test class, gated on `@EnabledIfEnvironmentVariable(named = "FOURTHBRAIN_MARKITDOWN", matches = ".+")`, runs the real converter against small fixtures committed under `src/test/resources/converter/`: a one-page digital PDF, a DOCX with headings and a table, an HTML file with non-ASCII text, an image-only PDF, a PDF encrypted with a user password, and a truncated PDF. These are synthesised, not drawn from the user's inflow, so they are safe to commit. The corpus in P2.8 stays where P2.8 put it.

## Acceptance criteria

1. `MarkdownConverter` exists in `com.fourthbrain.convert` with the three-method signature above. `Extractor` compiles against the interface and has no reference to `MarkItDownConverter`, `ProcessBuilder` or any string containing "python" or "markitdown".
2. `convert(path, "zip")` throws `ConversionException` with `Reason.UNSUPPORTED_FORMAT`, and no process is started, even when `zip` has been added to `supported-extensions` in the test configuration.
3. `convert(path, "md")` and `convert(path, "txt")` throw `UNSUPPORTED_FORMAT` and start no process.
4. With a faked runner that never exits, `convert` returns within `timeout + 5 s` with `Reason.TIMEOUT`, and the runner records that destroy was called. With the real converter and a `timeout` of `1s` against any fixture large enough to exceed it, no `markitdown` process is alive 10 s after `convert` returns (checked with `ProcessHandle.allProcesses()`).
5. A PDF encrypted with a user password does not return Markdown. `convert` throws with `Reason.CONVERTER_FAILED` or `Reason.EMPTY_RESULT`, the `detail` is non-blank and under 8 KiB, and the calling thread runs the next conversion successfully in the same test method.
6. An image-only PDF throws `Reason.EMPTY_RESULT`, not a blank string and not a success.
7. A truncated PDF throws `Reason.CONVERTER_FAILED` with the converter's stderr excerpt in `detail`.
8. An HTML fixture containing `Prüfung — 日本語` produces Markdown containing all three of those substrings when read back as UTF-8. This test runs on Windows in CI or is run by hand on the target machine and its output recorded in the story's completion note.
9. A DOCX fixture with two heading levels and a two-column table produces Markdown containing `# `, `## ` and a `|` row. This is a smoke check on structure, not a quality judgement — quality is P2.8's business.
10. A file whose name contains a space and an `&` converts successfully.
11. `Files.size(source)` above `max-input-bytes` throws `TOO_LARGE` with no process started.
12. Output above `max-output-bytes` throws `OUTPUT_TOO_LARGE`; the oversized file is deleted.
13. After every test in the suite, the configured `work-dir` contains no `in-*`, `out-*`, `err-*` or per-call directories.
14. With `executable` pointing at a nonexistent path and `fail-fast: true`, application startup fails and the log contains the attempted absolute path and a remediation line. With `fail-fast: false`, startup succeeds, one ERROR is logged, and `convert` throws `UNAVAILABLE` without starting a process.
15. With `expected-version` set to a value the installed converter does not report and `version-check: fail`, startup fails; with `warn`, startup succeeds and one WARN is logged.
16. Ten concurrent `convert` calls on the same fixture from ten threads all succeed, and at no point do more than `max-concurrent-processes` child processes exist.
17. `ConverterProperties` binds every key listed above from a test `application.yaml`, including `timeout` as a `Duration` written `120s`.
18. The `Reason` to status mapping table is copied into P2.3 verbatim, and P2.3's `depends-on` reads `P2.8, P2.9`.

## Out of scope

- **The actuator rewrite.** P2.3 owns calling this converter, archiving the original to the raw vault area, writing the Markdown and its front matter, setting status, and routing to the Classifier. P2.9 adds no call site in `Extractor`. The only production change outside `com.fourthbrain.convert` is the `application.yaml` block and, if needed, the status enum constants the mapping table requires.
- **ZIP.** Archive expansion stays in Java under P1.8. The converter rejects `.zip` by design, and that rejection is a tested criterion rather than an omission.
- **OCR.** The local PDF path is text extraction. A scanned page yields `EMPTY_RESULT` and a document sitting in `EXTRACTION_EMPTY` waiting for a story that does not exist yet. If P2.8 finds that a meaningful share of the corpus is scanned, that story becomes urgent, and it is still not this one.
- **Image description and audio transcription.** Both are paid or local LLM calls and both belong to the Classifier's budget, not the Extractor's. `--keep-data-uris` stays off for the same reason.
- **Azure Document Intelligence.** A paid external call and a separate decision.
- **A Tika implementation.** If P2.8 chooses Tika, the class that replaces `MarkItDownConverter` is a different story, and one of the two is deleted rather than both being kept.
- **A sidecar, a persistent worker, or MCP.** The interface is what makes any of them a later substitution. None of them is built here.
- **A Java MCP client.** P2.5's question, answered by P2.5.

## Contingent on P2.8's measurements

I cannot settle any of the following here. This is running as a batch job with no access to the user's documents, the target machine, or a Python install, so per-file output quality, wall-clock latency and install footprint are not measurable from where I am sitting. What follows are the places where this design has a placeholder waiting for a number, and the specific thing to run.

1. **Whether `MarkItDownConverter` is the right class at all.** Everything in the Design section except the class body applies unchanged to a Tika implementation. If P2.8's per-file verdicts show Tika's Markdown is good enough for the Classifier across the corpus, and Python 3.10+ is not already on the machine, the install cost tips it. Run the quality arm first; it decides whether the rest matters.
2. **`timeout`.** 120 s is a placeholder, not an estimate of anything. Replace it with the slowest per-document wall time measured across the corpus, rounded up and multiplied by three. Run: each fixture converted five times warm, record the maximum.
3. **Subprocess against sidecar.** Run `markitdown` against a 20-byte HTML file, twenty times, and record the wall time. `magika` loads a bundled ONNX model at import, so this cost may be well above bare interpreter startup — that is the number to get, and the brief does not have it. Compare it against the Classifier's per-document Ollama time on the same machine. If startup is a small fraction of the LLM call, subprocess stands and `max-concurrent-processes` can stay at 2. If it is comparable, reopen the sidecar with the measurement attached.
4. **`-x` with a file argument.** The staging step in the Design section exists because I do not know whether `-x` is honoured when a path is passed rather than stdin. Run `markitdown some-file.dat -x .html -o out.md` and see. If it works, staging is still cheaper to keep than to argue about, but the ADR should record what the flag actually does.
5. **`--version`.** Confirm the flag exists and record its exact output, so the version check parses something real. Pin `expected-version` to the version measured and set `version-check: fail`.
6. **`max-input-bytes`.** 100 MiB comes from the brief's failure-behaviour list, not from the corpus. Check the largest real input and whether the converter survives it.
7. **Which side of the WSL boundary Python lives on.** If the JVM runs on Windows and the venv in WSL2, every path in the command line needs `C:\...` to `/mnt/c/...` translation, and this design does none of that. Keep the interpreter on the same side as the JVM. Record which side that is in the ADR, because the `executable` path in `application.yaml` is meaningless without it.
8. **`min-output-chars`.** Left at 1, meaning "no non-whitespace at all". If the corpus contains digital PDFs that yield a handful of junk characters rather than nothing, raise it and record the value that separated the real documents from the empty ones.
