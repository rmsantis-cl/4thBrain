# Story P1.20 — Live Document Status in the Receipt Feed

## Problem

P1.18 put a receipt in the composer feed for every submission. It reads

```
Doc #42 [notes.md] — ingesting — File received and queued
```

and it never changes again. The document behind it moves through `ingesting` → `ingested` →
`classifying` → `classified` → `indexing` → `indexed`, and the box the user is looking at says
`ingesting` until the page is reloaded.

The idea this story exists to build: **that box should show the states the document is going
through.** The receipt is already the right shape and the right place — it is per-document, it is
where the user's attention is after they press SEND, and it is the only thing on the screen that knows
which document is theirs.

Nothing can report it today. `/api/status` returns five aggregate counts — how many documents are
classifying, not which ones — so the UI can say four documents are indexing and never say that *this*
document just finished. This is logged as **DD-2**, and both ADR27 and `plan-P1.18.md` name it as the
first thing to revisit if the single screen feels flat. It does.

## Step 0 — the design gate, ADR32

**ADR32 is reserved by this story.** ADR29 belongs to `plan-P2.2.md`, ADR30 to `plan-P2.5.md` and
ADR31 to `plan-P2.4.md`; do not reuse a number a parallel branch has claimed.

Four questions, and the first is the one that decides the shape.

### Q1 — a polled current status, or a stream of transitions?

This is not the usual poll-versus-push trade. It is a question about what is knowable at all.

**`document.status` holds one value: where the document is now.** No transition history is recorded
anywhere — there is no status-history table, and `document_copy` records locations rather than states.
So a poller can only ever ask "where is it now", and it will miss any stage that begins and ends
between two polls. `Ingestor.doTheThing` on a text document is a few string comparisons and a routing
decision; `ingesting` → `ingested` can be over in under a millisecond. A one-second poll will show
`ingesting`, then `indexed`, and the states in between will simply never have existed as far as the
UI is concerned.

That matters because the ask is to show the states the document *went through*, not a spinner that
eventually turns into a tick. Three ways to satisfy it:

| | Shape | Cost |
|---|---|---|
| **A — poll current status** | `GET /api/documents/{id}/status`, or a batch form for the open receipts | Cheapest. No new dependency, no publish hook, no connection lifecycle. **Shows a sampled path, not the real one** — fast stages are invisible, and the sequence differs run to run |
| **B — server-sent events** | `GET /api/documents/{id}/events`, or one stream for the session, `SseEmitter` on the existing servlet stack | Real transitions, in order, none missed. Needs a publish point at every status write, an emitter registry with timeout and cleanup, and a heartbeat. One-way server→client, which is exactly the traffic this has |
| **C — record transitions, then poll** | A `document_status` history table written on each status change; the endpoint returns the list since a cursor | Real transitions, and they survive a page reload — a receipt reopened tomorrow can still show what happened. Costs a schema change and a row per hop |

**Recommendation: C for the record, B for the delivery, and say plainly that A is not enough.** They
are not exclusive — the history table is what makes the sequence true, and the stream is what makes it
timely. If only one is built first, build C: a polled endpoint over a real transition log is honest
about the path, where a polled endpoint over a single column is not, and it is the half that cannot be
retrofitted from the client side.

Whichever is chosen, **the UI reads one model** — an ordered list of `(state, timestamp)` for a
document — so the transport can change later without touching the composer.

### Q2 — where does a status change get published from?

Any option but A needs one place that knows a status changed. There is no such place today, and this
is where the story collides with existing debt.

**DD-1 is in the way.** `Coordinator.startChain` writes status through `DatabaseService`
(synchronized, ADR17, and what ADR26 decision 6 names as the sole writer). `Actuator.run()` writes it
through `DocumentService.setStatus`, which is unsynchronized and which ADR26 retired. So the first
write of a chain and every write after it go through different services. A publish hook added to one
of them fires for some transitions and not others, and which ones depends on where in the chain the
document is — the worst possible failure for a feature whose whole purpose is showing a complete
sequence.

**So ADR32 either closes DD-1 or is blocked by it.** Closing it is the better answer and is small:
point `Actuator.run()` at `DatabaseService.updateDocumentStatus`, and decide DD-1's second half —
whether the actuator also sets the status on the in-memory `Document` travelling in the `Message`
(ADR26 decision 2). Note that `Actuator.java` is frozen while the four parallel Phase 2 plans are in
flight, so this story sequences after they merge.

One more thing to fix in the same pass, because it will otherwise produce wrong timestamps:
`DocumentService.updateDocumentStatus` sets `updatedAt`; `DatabaseService.updateDocumentStatus` does
not. Consolidating on the latter without adding the timestamp would leave every status change
unstamped.

### Q3 — does a receipt follow the document's children?

A URL submission does not finish in the document the receipt names. `Clipper` fetches the page,
creates a **child** `Document` with `parentId` set, and hands the child to the Ingestor; the parent
stops at `clipped`. A ZIP is the same shape — `Extractor` creates one child per member (P1.8) and the
parent ends at `extracted`.

So a receipt that watches only its own id shows a URL capture reaching `clipped` and then going quiet
forever, which reads as a stall. `Document.parentId` makes the children queryable, so the options are
to follow them, to show the parent's terminal state as a link to what it spawned, or to say nothing —
but the choice has to be made rather than discovered.

Note while deciding: `Clipper` leaves its child at status `New` when it enqueues it (recorded against
BUG-003's neighbourhood, owned by no story yet), so a followed child may sit at `New` for reasons that
have nothing to do with this feature.

### Q4 — what does a failed document look like?

**It cannot look like anything, and that is DD-4.** `Actuator.run()` stamps the participle
unconditionally after `doTheThing` returns, so a stage that failed leaves the document reading exactly
as if it had succeeded. An Indexer that could not write to the vault produces a document at `indexed`.

A live status strip makes this worse rather than neutral: today the lie is in a database column nobody
reads, and after this story it is on screen, in green, in front of the user. ADR32 has to either close
DD-4 or state in writing that the strip shows apparent progress and cannot show failure. The first is
the honest answer, and it is the same three lines of `Actuator.run()` that DD-1 touches — which is an
argument for doing DD-1 and DD-4 together, once, as this story's step 0.

## Change

Subject to ADR32. The shape the story expects:

1. A per-document status endpoint under `/api/documents/{id}`, returning an ordered list of
   `(state, at)` plus whatever Q3 decides about children. It is a new controller, not a widening of
   `StatusController` — DD-2 already records that P1.12's acceptance criteria are written entirely
   about aggregate counts, and widening that story from the outside makes it a different story.
2. Whatever Q1 and Q2 settle: a transition record on each status write, a publish point, and the
   delivery mechanism.
3. In `index.html`, the receipt grows from one line into a small state strip — the states so far, the
   current one marked, each with an elapsed time. It stays inside the existing `.feed-entry.receipt`
   box, and it stops updating when the document reaches a terminal state.
4. Receipts stop updating on page unload, and the page does not accumulate connections or timers for
   documents that finished.

## Acceptance criteria

- Submitting a note through the composer produces a receipt whose box shows each state the document
  reaches, in order, without a page reload
- Every transition the pipeline performs appears — a stage that completes in under a millisecond is
  not silently absent (this is what Q1 turns on)
- A URL submission's receipt behaves as ADR32 decides for Q3, and does not read as a stall
- The strip stops at a terminal state and the page holds no live connection or timer for it afterwards
- Ten submissions in a row do not leave ten open connections or ten running pollers
- The receipt still renders correctly when the status endpoint is unreachable — it falls back to the
  single line P1.18 already produces, rather than showing an empty box
- Nothing on the screen claims success for a document whose stage failed, or ADR32 records in writing
  that it does (Q4)
- DD-2 marked Cleared in `documents/DESIGN-DEBT.md`

  should agree on how a status is spelled.

## Notes

The states themselves are already defined and are worth having in one place while designing the strip.
Each actuator declares a gerund and a participle, and `Actuator.run()` writes the gerund on pickup and
the participle on completion:

| Stage | While working | When done |
|---|---|---|
| Ingestor | `ingesting` | `ingested` |
| Extractor | `extracting` | `extracted` |
| Clipper | `clipping` | `clipped` |
| Classifier | `classifying` | `classified` |
| Indexer | `indexing` | `indexed` |

The path through them is not fixed — it is chosen per document by `Ingestor.doTheThing`, and
`plan-P2.2.md` changes it under ADR29 so that text reaches the Classifier instead of going straight to
the Indexer. A strip that hardcodes a five-stage pipeline will be wrong for a URL, wrong for a ZIP, and
wrong again after P2.2 merges. Render the states that actually arrive.

Origin: the idea came from looking at P1.18's receipt boxes in use and asking what else the box could
show. That is exactly the evaluation ADR27 said the composer's first run was for, so it belongs in
P1.17's and P1.18's record as well — the single screen is working well enough that its next limitation
is visible.
