# Story P1.16 — Crash Recovery

Drafted as P1.15 on the branch that carried the P1.9/P1.10 verification work. Renumbered to
P1.16 when that branch was rebased, because P1.14 was already taken by View Layer & Template
Engine and the renumber cascaded.

## Problem

Documents can be left in a transient status if an actuator or the application crashes
mid-processing.

A document with status `ingesting` when the application exits has no actuator-owned queue entry
— it was already polled. On restart that document sits in `ingesting` forever: no actuator picks
it up, and no endpoint can tell what went wrong.

## Change

1. On startup, query for documents in any transient status — the gerund forms `ingesting`,
   `extracting`, `classifying`, `indexing`.
2. For each, look at the last update's timestamp. If it is older than a configured threshold
   (1 hour since the last status change), assume the previous actuator crashed and requeue the
   document to that stage.
3. Handle documents with no status history — newly created but never started. Requeue them to
   `Ingestor`.
4. Log a recovery report: how many documents were requeued, from which stages. This shows up in
   the startup log and flags a crashed run.
5. Reconcile with the vault: a document marked `indexing` but already present in the vault is
   marked indexed rather than requeued, so an indexer crash that persisted its work is not
   re-run.

## Acceptance Criteria

- A document left in `ingesting` with a timestamp more than 1 hour old is requeued to the first
  actuator on startup
- A document in `indexing` that is present in the vault is marked `indexed` instead of requeued
- The startup log contains a recovery report — "Recovered 3 documents from ingesting, 1 from
  classifying"
- Requeue does not duplicate work: one document's ID is not enqueued twice in a single startup
- A document in a transient status for less than 1 hour is left alone; it may still be in
  progress

## Orphaned documents and their files — a decision this story owns

**Deferred deliberately, 2026-09-08.** There is already a backlog of exactly the documents this
story exists to recover, and a matching backlog of files on disk. The decision about what to do with
them belongs here rather than to whatever change happens to notice them next.

What exists today:

- Documents parked in a transient status with no queue entry and no actuator coming for them.
  BUG-004 left at least one — document 13, `Retro skill`, stuck at `ingested` because its type could
  not be resolved, so `Ingestor` returned null. Its status reads like success, which is DD-4.
- Around two dozen extensionless files in `tmp/` — `archive`, `document`, `document_001`,
  `large-document` and so on — one per upload that lost its suffix under BUG-004. Their documents are
  the parked ones.

The two are the same backlog seen from the database and from the filesystem, which is why this story
is the right owner: criterion 5 already says a document must be reconciled against the vault rather
than blindly requeued, and these need the same reconciliation in the other direction — a file with no
usable document, and a document whose file is unusable.

**What has to be decided when this story runs:**

1. **Requeue, or abandon?** BUG-004's documents were not interrupted mid-flight; they completed a
   stage that could not classify them. The one-hour threshold in criterion 2 would sweep them up, and
   requeuing them now that MIME resolution works would probably succeed — but "the code that failed
   you has since been fixed" is not something the recovery pass can know. Decide whether recovery
   requeues on age alone or needs a reason recorded on the document, which is DD-4 again.
2. **The files with no extension.** Their `document_copy` rows point at real bytes whose type is
   unknown. Re-resolving from the database's `name` is possible for some and not for others.
3. **Whether recovery ever deletes anything.** Nothing in this project currently removes a file, and
   a recovery pass that does is a different risk profile from one that only requeues.

**Until then, the files stay where they are.** `tmp/` is in `.gitignore` and, as of 2026-09-08, is no
longer tracked — 29 files under it had been committed before the ignore rule existed, and
`.gitignore` does not retroactively untrack. They remain on disk untouched, which is the intended
interim state, not an oversight.

## Phase Placement

Placed in Phase 1, but it is operational rather than structural work and may be better deferred
until the core pipeline is proven — Phase 2 or Phase 3. The backlog described above is an argument
for not deferring it too far: it grows with every failure the pipeline cannot report.
