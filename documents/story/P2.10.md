# Story P2.10 — Deploy Ollama on Windows

## Problem

`application.yaml` already points at Ollama:

```yaml
ollama:
  url: http://localhost:11434/v1
  model: mistral
  concurrency: 1
```

Nothing in the repository installs it, starts it, or pulls that model, and no story owns doing so.
Ollama is an NFR2 dependency of the whole classify-and-brief half of the pipeline, so P2.1 cannot
meet its own acceptance criterion — "OllamaClient successfully calls Ollama and parses responses" —
on a machine where the port answers nothing. P2.4, P2.6 and the P3.4 smoke test inherit the same
gap.

This is an environment story. It changes no production code; what it produces is a working local
service and a runbook that gets a second machine to the same place.

## Decisions to settle

1. **Native Windows install, not WSL2.** The JVM runs on Windows and reaches `localhost:11434`
   directly, the installer registers a startup entry, and GPU access needs no passthrough setup.
   Record WSL2 as the rejected alternative with the reason, since NFR1 names both.
2. **Model and tag.** `application.yaml` says `mistral`, a floating tag — the model behind it can
   change under a later `ollama pull`. Pin an explicit tag so classification behaviour does not
   drift, and update `application.yaml` to match. Confirm the pinned tag still exists upstream
   before writing it down.
3. **Model storage location.** A 7B model at 4-bit quantisation is roughly 4–5 GB and lands in
   `%USERPROFILE%\.ollama` by default. If the system drive is tight, set `OLLAMA_MODELS` to another
   drive before the first pull; moving models afterwards means relocating a blob store by hand.
4. **Autostart.** The installer's tray app runs at login, which covers a desktop someone signs into.
   Decide whether that is enough or whether the pipeline has to survive an unattended reboot. If it
   does, the service question needs an answer rather than a shrug.
5. **Keep-alive.** Ollama unloads an idle model after five minutes. With `concurrency: 1` and a
   Briefing that fires once at 6 AM, most calls will pay a cold load. Decide whether to raise
   `OLLAMA_KEEP_ALIVE`, and record the memory it costs to hold the model resident.

## Change

1. Install Ollama for Windows and record the installed version.
2. Set `OLLAMA_MODELS` — and `OLLAMA_KEEP_ALIVE`, if decision 5 says so — as user environment
   variables, before the first pull.
3. Pull the pinned model. Record the download size and the resident memory it uses under load.
4. Confirm it starts on login, and that a reboot leaves the port answering with no manual step.
5. Verify the OpenAI-compatible surface specifically. The app calls `/v1/chat/completions`, not
   `/api/generate`, so a green `/api/tags` proves less than it looks like it does:
   - `ollama list` shows the pinned model.
   - `Invoke-RestMethod http://localhost:11434/api/tags` returns it.
   - A POST to `http://localhost:11434/v1/chat/completions` with `{"model": "<pinned>",
     "messages": [{"role": "user", "content": "reply with the single word ok"}]}` returns a
     `choices[0].message.content`.
   - Record wall time for that call. It is the per-document floor the Classifier inherits, and
     ADR28's trigger 3 wants it as its comparison point.
6. Update `application.yaml`'s `ollama.model` to the pinned tag if it differs from `mistral`.
7. Write the runbook to `documents/design/OLLAMA-SETUP.md`: version, install steps, environment
   variables, the pull command, the verification commands above with their expected output, and
   what to check first when the port does not answer.
8. Record the hardware the measurements came from — CPU, RAM, whether a GPU was used. CPU-only and
   GPU runs differ by enough that a timing with no machine attached is not worth keeping.

## Acceptance Criteria

- `ollama --version` reports a version, and that version is written in the runbook
- The pinned model appears in `ollama list`, and `application.yaml` names the same tag
- A POST to `http://localhost:11434/v1/chat/completions` returns a completion, with its wall time
  and the machine it ran on recorded
- After a reboot with no manual start, the same POST still succeeds
- `documents/design/OLLAMA-SETUP.md` exists and is complete enough that a second Windows machine
  reaches a passing verification from it alone
- The WSL2 alternative is recorded as considered and rejected, with the reason

## Out of Scope

- `OllamaClient` and `ConcurrencyGate`. P2.1 builds those against the service this story stands up
- A scripted health check, or a startup probe inside the application. Both are production code and
  would need their own story and design; verification here is manual and documented
- Model choice on quality grounds. This story pins whatever tag the project already names and stops
  that tag from floating. Whether a different model classifies better is separate work
