# Story P2.10 — Deploy Ollama on Windows

## Status

**COMPLETED 2026-09-08.** Closed on the decision that the environment work is done and what remains
in Phase 2 is the missing actuators. Ollama is installed and answering; the documentation half of the
story is not done and is recorded here rather than quietly dropped.

Verified on the development machine, 2026-09-08:

| Check | Result |
|---|---|
| `ollama --version` | `0.33.3` |
| Service answers on `localhost:11434` | Yes — `/api/tags` returns |
| Models present | `devstral:24b` (14 GB), `gemma4:12b` (7.6 GB) |

Three acceptance criteria are met: a version is reported, the port answers, and the service was
running without anyone starting it by hand for this session.

Four are not, and each is carried somewhere:

- **`application.yaml` names a model that is not installed.** `ollama.model` is `mistral`; `ollama
  list` has `devstral:24b` and `gemma4:12b`. The first real Classifier call will get a
  model-not-found from Ollama. This has never surfaced because P2.4 closed with every test against a
  hand-written fake `OllamaClient`, so nothing in the test suite ever asks the server for a model.
  **This is a live defect, not a documentation gap.** Fixing it means choosing a tag, which is
  [[P2.11]]'s subject and `design/SPIKE-LOCAL-MODEL-SELECTION.md`'s recommendation.
- **No runbook.** `documents/design/OLLAMA-SETUP.md` was not written, so the "a second Windows machine
  reaches a passing verification from it alone" criterion is unmet. Nothing depends on it today.
- **No recorded wall time** for a `/v1/chat/completions` round trip. ADR28's trigger 3 wants that
  number as its comparison point for conversion cost, and [[P2.11]] records it per model anyway.
- **No reboot check, and the WSL2 rejection is not written down.** The native-Windows decision was
  taken (decision 1 below) and the alternative's reasoning lives in this file rather than in a
  runbook.

Neither installed model is what the spike recommends, and neither was chosen for this pipeline —
`devstral` is a coding model and a poor fit for classification, and both are large enough on CPU that
the spike's throughput table puts them at a few tokens per second. The candidate set for [[P2.11]]
starts from what is already local rather than from nothing.

## Problem

`application.yaml` already points at Ollama:

```yaml
ollama:
  url: http://localhost:11434/v1
  model: mistral
  concurrency: 1
```

Nothing in the repository installs it, starts it, or pulls that model, and no story owns doing so.
Ollama is an NFR2 dependency of the whole classify-and-brief half of the pipeline, so P2.1 cannot
meet its own acceptance criterion — "OllamaClient successfully calls Ollama and parses responses" —
on a machine where the port answers nothing. P2.4, P2.6 and the P3.4 smoke test inherit the same
gap.

This is an environment story. It changes no production code; what it produces is a working local
service and a runbook that gets a second machine to the same place.

## Decisions to settle

1. **Native Windows install, not WSL2.** The JVM runs on Windows and reaches `localhost:11434`
   directly, the installer registers a startup entry, and GPU access needs no passthrough setup.
   Record WSL2 as the rejected alternative with the reason, since NFR1 names both.
   **Settled as stated** — the installed service is the native Windows build.
2. **Model and tag.** `application.yaml` says `mistral`, a floating tag — the model behind it can
   change under a later `ollama pull`. Pin an explicit tag so classification behaviour does not
   drift, and update `application.yaml` to match. Confirm the pinned tag still exists upstream
   before writing it down.

   `design/SPIKE-LOCAL-MODEL-SELECTION.md` answers *which* tag for a CPU-only machine, and its
   recommendation is not `mistral`: a 4B-class model at Q4_K_M, on the grounds that with no VRAM the
   limit is memory bandwidth rather than capacity, and that the current tag resolves to the older
   Q4_0 quantisation.

   **Not settled.** `mistral` was never pulled, so the config names nothing the server can serve.
   The decision moves to [[P2.11]], which chooses on measured evidence rather than on the spike's
   argument alone. Until it runs, whoever needs a working Classifier pins one of the two local
   models by hand.
3. **Model storage location.** A 7B model at 4-bit quantisation is roughly 4–5 GB and lands in
   `%USERPROFILE%\.ollama` by default; a 4B model is nearer 2.5 GB. If the system drive is tight, set
   `OLLAMA_MODELS` to another drive before the first pull; moving models afterwards means relocating
   a blob store by hand. **Left at the default**, with about 22 GB of models already there.
   [[P2.11]] pulls more to compare them, so leave room for the set rather than for one.
4. **Autostart.** The installer's tray app runs at login, which covers a desktop someone signs into.
   Decide whether that is enough or whether the pipeline has to survive an unattended reboot. If it
   does, the service question needs an answer rather than a shrug. **Left at the tray app**, which is
   enough for a desktop someone signs into; the unattended case is untested.
5. **Keep-alive.** Ollama unloads an idle model after five minutes. With `concurrency: 1` and a
   Briefing that fires once at 6 AM, most calls will pay a cold load. Decide whether to raise
   `OLLAMA_KEEP_ALIVE`, and record the memory it costs to hold the model resident — which is the
   model's own size. The spike recommends raising it, and pairing it with
   `OLLAMA_NUM_PARALLEL=1` to match P2.1's single-permit `ConcurrencyGate`. **Not set.** At 7.6 GB
   for the smaller local model, holding it resident is a real memory commitment on a 32 GB machine,
   and the number changes once P2.11 picks a smaller model.

## Change

1. Install Ollama for Windows and record the installed version.
2. Set `OLLAMA_MODELS` — and `OLLAMA_KEEP_ALIVE`, if decision 5 says so — as user environment
   variables, before the first pull.
3. Pull the pinned model. Record the download size and the resident memory it uses under load.
4. Confirm it starts on login, and that a reboot leaves the port answering with no manual step.
5. Verify the OpenAI-compatible surface specifically. The app calls `/v1/chat/completions`, not
   `/api/generate`, so a green `/api/tags` proves less than it looks like it does:
   - `ollama list` shows the pinned model.
   - `Invoke-RestMethod http://localhost:11434/api/tags` returns it.
   - A POST to `http://localhost:11434/v1/chat/completions` with `{"model": "<pinned>",
     "messages": [{"role": "user", "content": "reply with the single word ok"}]}` returns a
     `choices[0].message.content`.
   - Record wall time for that call. It is the per-document floor the Classifier inherits, and
     ADR28's trigger 3 wants it as its comparison point.
6. Update `application.yaml`'s `ollama.model` to the pinned tag if it differs from `mistral`.
7. Write the runbook to `documents/design/OLLAMA-SETUP.md`: version, install steps, environment
   variables, the pull command, the verification commands above with their expected output, and
   what to check first when the port does not answer.
8. Record the hardware the measurements came from — CPU, RAM, whether a GPU was used. CPU-only and
   GPU runs differ by enough that a timing with no machine attached is not worth keeping. Record the
   memory *speed* as well as the size: the spike's throughput estimates turn on whether this is DDR4
   or DDR5, and nothing else distinguishes the two columns of its table.

## Acceptance Criteria

- ✅ `ollama --version` reports a version — `0.33.3`, recorded in the Status section above rather
  than in a runbook
- ❌ The pinned model appears in `ollama list`, and `application.yaml` names the same tag —
  `application.yaml` names `mistral`, which is not installed
- ❌ A POST to `http://localhost:11434/v1/chat/completions` returns a completion, with its wall time
  and the machine it ran on recorded — the port answers on `/api/tags`, and the completion surface
  was not exercised with a timing
- ❌ After a reboot with no manual start, the same POST still succeeds — not tested
- ❌ `documents/design/OLLAMA-SETUP.md` exists and is complete enough that a second Windows machine
  reaches a passing verification from it alone — not written
- ✅ The WSL2 alternative is recorded as considered and rejected, with the reason — in decision 1 of
  this file, not in a runbook

## Out of Scope

- `OllamaClient` and `ConcurrencyGate`. P2.1 builds those against the service this story stands up
- A scripted health check, or a startup probe inside the application. Both are production code and
  would need their own story and design; verification here is manual and documented
- Model choice on quality grounds. This story pins a tag and stops it from floating; whether a
  different model classifies *better* belongs to [[P2.11]], which builds a labelled fixture set and
  measures it. `design/SPIKE-LOCAL-MODEL-SELECTION.md` is where the hardware argument for a
  candidate is made; P2.11 is what tests that argument's conclusion. Until it runs, no model output
  in this project has been compared against a human answer — Story P2.4 closed with every test using
  a hand-written fake
- `response_format: json_schema` on the Classifier's request, and a capped `num_ctx`. The spike
  argues both matter more than the model choice, and both are production code belonging to P2.4's
  successor rather than to an environment story. P2.11 treats structured output as a variable in its
  experiment rather than shipping it
