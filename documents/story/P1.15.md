# Story P1.15 — Orderly Shutdown

Drafted as P1.14 on the branch that carried the P1.9/P1.10 verification work. Renumbered to
P1.15 when that branch was rebased, because P1.14 was already taken by View Layer & Template
Engine.

## Problem

The application has no way to stop gracefully. Threads run forever, and shutdown relies on the
JVM exiting.

`Actuator.running` is private with no way to clear it from outside. `Actuator` extends `Thread`
but defines no `shutdown()` method. When Spring's `@PreDestroy` fires, nothing tells the threads
to stop, and they keep looping on their queues even though the context is shutting down. Daemon
threads will eventually be killed when the JVM exits, but nothing waits for in-flight work to
finish, and nothing closes resources cleanly.

Partly addressed already: `ActuatorManager.@PreDestroy` (P1.9) and `shutdown()` (P1.10) both
landed, and a context close now logs `Thread exiting.` once per actuator followed by
`Shut down N actuator thread(s)`. What remains is the endpoint and the join-timeout reporting.

## Change

1. Add `boolean running` as a volatile field and expose a `shutdown()` method on `Actuator`.
   `shutdown()` clears `running` and calls `interrupt()` on the thread.
2. In `Actuator.run()`, catch `InterruptedException` separately from other exceptions and treat
   it as a stop signal — clear `running` and leave the loop.
3. `ActuatorManager.@PreDestroy` calls `shutdown()` on every actuator, then `join(timeout)`. Log
   a thread that does not exit within the timeout and move on; the JVM will kill it, but this
   makes it visible.
4. Add a `/api/shutdown` endpoint (or a Spring Boot Actuator endpoint) that calls
   `ActuatorManager.shutdown()`, so the application can be stopped cleanly from outside — tests,
   orchestration, graceful restart.

## Acceptance Criteria

- **MET** — `shutdown()` stops an actuator's thread within a bounded time (5 seconds per thread).
  `ActuatorShutdownTest.shutdownStopsAnIdleThread` measures the elapsed time and asserts it is
  inside the bound. The bound is a property of the manager rather than of `shutdown()`, which no
  longer waits: `shutdownAll()` signals every actuator before joining any of them, so the joins
  do not stack. A thread still alive after `actuators.shutdown.join-timeout-ms` is named in a WARN
  and left to the JVM.
- **MET** — `Thread exiting.` is logged exactly once per actuator, at shutdown.
  `ActuatorShutdownTest` asserts the count through a Logback `ListAppender`, on a normal stop, on
  repeat `shutdown()` calls, and on a `shutdown()` that arrives before `start()` (where the count
  is zero, because the loop never ran).
- **HALF MET, HALF WAIVED** — in-flight documents either finish processing or are marked with a
  stopped status before the context closes. The first branch is built and tested:
  `inFlightWorkFinishes` holds a document inside `doTheThing`, calls `shutdown()` while it is
  there, and asserts the document reaches its participle before the loop exits. The second branch
  is waived on **DD-4** — `Actuator.run()` stamps the participle unconditionally, so there is no
  stopped status for the run loop to write and no way to add one without taking DD-4's fix in
  passing. ADR36 records this rather than leaving it inside the tick.
- **MET** — `shutdown()` on an already-stopped actuator is idempotent. `shutdownIsIdempotent`
  calls it twice more after the thread has ended and asserts nothing restarts and nothing is
  re-logged; `shutdownBeforeStartIsSafe` covers a thread that was never started.

## Verification

`gradle build` green: 122 tests, 0 failures, 0 skipped. Seven of those are this story's —
`ActuatorShutdownTest` (5) and `ShutdownControllerTest` (2).

**Nothing here was run against a live application.** Every check is a unit test.
`ShutdownControllerTest` sets `shutdown.close-delay-ms` past the life of the test on purpose, so
the endpoint's own daemon thread never reaches `SpringApplication.exit` — what the endpoint does
*after* it answers is not covered by anything. The claim that closing the context ends the process
rests on the argument in ADR36 (the web server holds the only non-daemon thread) and not on an
observed exit.

## Design

**ADR36** — `POST /api/shutdown` stops the application; the bounded join belongs to the manager.
Folded into `documents/design/ADRS.md`.

## Gaps recorded elsewhere

**DD-6.** A document whose message was already offered to the next actuator's queue is lost with
that queue when the context closes, and it sits at a participle, which P1.16 does not treat as
transient. Nothing recovers it. The gap is between this story and P1.16 rather than inside either.
