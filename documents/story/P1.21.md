# Story P1.21 — Spike: Generated Tracking Documents

## Problem

`BACKLOG-TRACKER.md` and `documents/INDEX.md` are two hand-maintained files that every agent has to
edit, and almost every edit is to a different row than the last one. Two agents closing two unrelated
stories both rewrite the summary counts, both append to the same changelog, both touch a table where
their rows sit lines apart. Git sees adjacent-line edits to one file and conflicts. Semantically
nothing overlapped at all.

The cost is measurable and already written down. `.claude/rules/batch-document-updates.md` exists
because closing Story P1.17 took 21 write operations across 7 files where 7 would have done — six
passes over `BACKLOG-TRACKER.md` alone. The rule reduces the symptom by asking for one write per file;
it cannot remove the cause, which is that a file everyone must edit is a file everyone collides in.

This session is fresh evidence:

- `BACKLOG-TRACKER.md` was edited about a dozen times across four turns.
- The changelog is ordered oldest-first, and a new entry landed in the wrong position **twice**, both
  times fixed by swapping two lines afterwards. Nothing in the file makes the ordering checkable.
- The Summary counts (`35 stories: 1 WIP, 10 READY, 8 NOT-READY, 16 COMPLETED`) were recomputed by
  hand four times. They are derived data maintained by arithmetic in an agent's head.
- `documents/INDEX.md` stores each file's history as `[date] comment` entries joined by `<br>` inside
  a table cell, a shape its own rule explains as a workaround: "Markdown tables cannot nest a table
  inside a cell". It is a list pretending to be a string.

And drift is the documented outcome when derived data is hand-kept. `.claude/rules/file-indexing.md`
records why `src/` stopped being indexed: 61 rows "had drifted badly from the code" — of 7 indexed
actuator files only one existed, all 4 `messaging/` rows were wrong, and a dozen files appeared twice
with conflicting descriptions.

## The idea

Stop treating the Markdown as the source of truth. Hold the facts as **one record per entity** —
a story, a bug, an indexed file — each in its own file, carrying its status, its dependencies and its
own history. Agents write records. At the end of a change, a generator **recreates**
`BACKLOG-TRACKER.md` and `documents/INDEX.md` from the records.

Two agents working on two different stories then write two different files and never meet. Counts
stop being arithmetic and become a `count()`. Changelog order stops being a thing to remember and
becomes a sort.

This spike designs that: the record format, where records live, what regenerates the documents, and
what happens to the three governance rules that currently describe hand-editing.

## What the spike must settle

### Q1 — where do the records live? **Settled: one shared SQLite database, across all projects.**

Decided 2026-09-08. Version 1.0 of this story recommended one file per entity inside this git repo
and argued SQLite lost on being binary in git, undiffable and unreviewable. **That recommendation is
superseded, and the reason is a requirement it did not have:** the store is to serve *every* project,
not this one. There are thirteen project directories under `~/.claude/projects` today. A directory of
records inside `4thBrain` cannot hold facts about another repository, so option A does not answer the
question actually being asked.

Two other things follow once the store is outside any repo, and both cut in SQLite's favour:

- **Concurrency stops being a merge problem and becomes a transaction.** Files in git only resolve two
  agents at merge time, and only if they touched disjoint paths. SQLite in WAL mode gives real
  locking between separate processes, so two agents writing two rows is simply correct — including
  agents running in the git worktrees this project already uses.
- **The reviewability objection survives, and has an answer.** A database change cannot be read in a
  pull request. But the generated `BACKLOG-TRACKER.md` and `documents/INDEX.md` are committed to the
  repo as they are today, so **the diff that gets reviewed is the regenerated Markdown**. The store
  holds the working state; the generated file in git is the reviewable, diffable, durable record of
  it. That also answers backup — see Q1b.

Rejected on the way:

| | Why not |
|---|---|
| A JSON file store | There is no JSON database here, and a directory of JSON files is option A with a different syntax — same cross-project problem, and now hand-rolled locking |
| A spreadsheet (`openpyxl 3.1.5` is installed, so it is possible) | A single binary file is the collision problem again and worse: no line-level merge at all, and two agents writing at once lose data rather than conflict. It reintroduces exactly what this story exists to remove |
| One file per entity in this repo (v1.0's recommendation) | Cannot hold another project's records |

No new dependency either way: `sqlite3.exe` 3.53.4 is on `PATH` and Python 3.11's stdlib carries
`sqlite3` 3.45.1, `json` and `csv`.

### Q1b — where does the database live, and what happens when it is lost?

Newly opened by Q1, and it has to be answered before anything is built, because the store becomes the
source of truth for every project at once — a single point of loss with a blast radius wider than any
one repo.

- **Path and ownership.** Somewhere machine-local and stable, outside every project tree — an
  `~/.claude`-adjacent location is the obvious candidate given what already lives there. Name it in
  the ADR; do not let each agent guess.
- **A rebuild path, not just a generate path.** The generator writes Markdown from the database. It
  also has to be able to *read* the committed Markdown back into records, or the database's loss
  destroys history that git was holding safely five minutes earlier. If the round trip is lossy, say
  what is lost.
- **Local only.** SQLite over a network share or a synced folder is unsafe under concurrent writers,
  which is the one property this design is buying. If two machines ever need it, that is a different
  design and the ADR should say so rather than leave it to be discovered.
- **Schema versioning.** A store shared by every project is a store that cannot be migrated one
  project at a time. It needs a version and a migration path from the first commit.

### Q1c — what does "all projects" mean in the schema?

Every row needs a project key, and the projects need naming once rather than per-agent.
`~/.claude/projects` already encodes them as flattened paths
(`C--Users-rsant-desar-github-4thBrain`), which is a usable key and an ugly one; a short slug with the
repo path recorded alongside is likely better. Worth settling: whether the key is the repository, the
working tree, or the product — this repo has worktrees, a `server` subdirectory and a v03 predecessor
all appearing as separate entries in that list.

### Q2 — what regenerates the documents, and is it deterministic?

**This is the question the whole idea turns on.** The story asks for "an agent" that recreates the
documents. There are two very different things that phrase can mean:

- **A deterministic generator** — a script that reads records and emits Markdown. Same records in,
  byte-identical file out, every time. Reviewable, testable, and a regeneration with no record change
  produces an empty diff.
- **An LLM writing the file from the records.** Flexible, and it destroys the property that makes this
  worth doing. Prose regenerated from the same input differs every run, so every regeneration churns
  the whole file, every diff is unreadable, and the collisions come straight back — worse, because now
  they are on lines nobody intended to change.

**Recommendation: the generator is a script; the agent writes records and invokes it.** That keeps the
agent doing the part that needs judgement — deciding what happened and describing it — and the script
doing the part that needs consistency. Record the split explicitly, because "an agent recreates the
document" is ambiguous and the wrong reading is the expensive one.

Second-order: the script is code, so it needs a home (`scripts/`), a language (PowerShell is the
project's shell; the build is Gradle and Java), and a test that proves determinism.

### Q3 — what happens to the prose?

The hard part, and the reason this is a spike rather than a task.

`BACKLOG-TRACKER.md` is not a table. It is four tables **plus** roughly a dozen paragraphs of genuine
argument — why P2.1–P2.7 were blocked and are not any more, why ADR28 was taken without measurements,
what the five parallel plans freeze and why, what `plan-11-13-17.md` was chosen over. None of that is
derivable from records, and it is the most valuable content in the file.

Three shapes:

| | Approach | Cost |
|---|---|---|
| **A — generated regions** | `<!-- BEGIN GENERATED: summary -->` … `<!-- END -->` markers; the script replaces only what is between them and never touches prose | Prose stays where it reads best. The file is still one file, so two agents editing two *notes* still collide — but that is rare and it is a real conflict |
| **B — notes become records too** | Each note is a record with an order key | Everything generated, nothing collides. Editing a paragraph means editing YAML, and long prose in YAML is unpleasant to write and to review |
| **C — split the file** | `BACKLOG-TRACKER.md` fully generated; the essays move to a companion document | Clean separation. Costs a second file to look in, and the notes lose the tables they refer to |

**Recommendation: A**, with the summary, the four status tables and the changelog inside markers and
the notes outside. It removes the collisions that actually happen without forcing prose into a data
format.

### Q4 — what does a record contain?

At minimum, for a story: id, title, status, dependencies, what it blocks, the file it details, and a
list of history entries each with a date and a comment. That covers the tracker's tables and the
INDEX's history cell from one shape.

Points to settle rather than assume:

- **Where is the story's own prose?** `documents/story/P1.18.md` already exists and already has a YAML
  header carrying `status`, `depends-on` and `blocks`. So the record may not need to be a new file at
  all — the story file's own header could be the record, read by the generator. That is one fewer
  place for the truth to live and one fewer thing to keep in sync, and it is a strictly better answer
  if the header can carry everything. Check whether it can before inventing `documents/meta/`.
- **Status vocabulary**, spelled once. Story headers and the tracker already disagree today: P2.10's
  header says `READY` while the tracker says COMPLETED, and P2.1, P2.2, P2.4 and P2.5 all say
  `NOT-READY` against a tracker listing them READY. A generator makes that class of drift impossible,
  which is an argument for this whole idea and also the first thing migration has to reconcile.
- **History entries need a stable sort.** Date alone is not enough — this session produced three
  entries on 2026-09-08 whose order matters. A sequence number, or a timestamp rather than a date.

### Q5 — what is the one contended resource?

Disjoint files remove almost all collisions, but not the allocation of the next id. Two agents both
creating a story concurrently both want the next free number, and both will pick it. The same is true
of ADR numbers — this repository already handles that by hand, reserving 29, 30, 31, 32 across five
in-flight plans and writing the reservations into the tracker so nobody reuses one.

The spike should say whether that stays a human convention or becomes something the generator checks
(a duplicate-id error at regeneration time is cheap, catches it late but reliably, and needs no
coordination protocol).

### Q6 — what happens to the three rules that describe the current way?

`.claude/rules/batch-document-updates.md` exists to reduce collisions that this design removes.
`.claude/rules/file-indexing.md` describes hand-maintaining INDEX rows. `.claude/rules/file-versioning.md`
requires a `version` bump and a `date` on every save, which for a generated file is either meaningless
or the generator's job.

All three need rewriting or retiring as part of this, and none of it should be discovered afterwards.
`documents/simple-claude-plan.md` is already an audit of the governance layer proposing to cut nine
rules to five; this spike should be read against it rather than beside it.

## Acceptance criteria

- A written decision recorded as **ADR33**, answering Q1b through Q6 and restating Q1's settled answer
  with its reasoning
- A SQLite schema with a version, a project key, and a worked example for one story, one bug and one
  indexed file, taken from real current content rather than invented
- The database path, ownership and creation-on-first-use behaviour named explicitly (Q1b)
- **A rebuild check:** delete the database, rebuild it from the Markdown committed in the repo, and
  regenerate. Whatever does not survive that round trip is the story's most important finding, because
  it is what a lost database costs
- A statement of whether story file headers can serve as the records (Q4), tested against three real
  story files, and if not, why not. Under Q1's answer the headers are no longer a candidate *store* —
  they cannot hold another project's records — but they remain the best candidate **input**, and the
  cheapest first population of the database
- A concurrency check: two processes writing records for two different stories at once, both
  committed, neither lost
- A prototype generator producing `BACKLOG-TRACKER.md` and `documents/INDEX.md` from records, run
  against the current backlog
- **A determinism check:** regenerating twice with no record change produces a byte-identical file
- **A fidelity check:** the generated `BACKLOG-TRACKER.md` is diffed against the hand-maintained one
  and every difference is either an improvement or explained. This is the criterion that says whether
  the idea works — if the generated version loses something, that is the finding
- A migration note: how existing content moves into records, and what reconciles the status
  disagreements Q4 lists
- A statement of what happens to the three `.claude/rules/` files in Q6
- A follow-on implementation story, blocked by this one
- **No production code and no governance change lands under P1.21.** The prototype lives outside
  `scripts/` until the follow-on story adopts it

## Scope

**In:** `BACKLOG-TRACKER.md` and `documents/INDEX.md`. Those are the two the user named, they are the
two every agent edits, and they are the two that are almost entirely derived.

**Out, deliberately:**

- **Story files, bug files, ADRs, plans and design documents.** These are the actual content, written
  once by whoever is thinking about them, and rarely touched by a second agent at the same time.
  Generating prose is Q2's failure mode. `documents/story/P1.18.md`'s header may be *read* as a
  record; the body stays hand-written.
- **`documents/DESIGN-DEBT.md`.** Five entries, mostly argument, appended rarely. Revisit if this
  works.
- **`INDEX.md` at the repository root and `scripts/INDEX.md`.** Same treatment eventually; start with
  the one that hurts.
- **Anything about the product.** This is tooling for how the project records itself.

## Notes

**The store is cross-project; this story is not.** Q1's answer makes the database serve every project,
which means the follow-on implementation is a piece of personal tooling that happens to be designed
here because this is where the pain showed up. Two consequences the ADR should state: 4thBrain's own
repository should not be the home of a tool other projects depend on, and a schema shared by
everything cannot be changed by one project in isolation. Where the generator's code actually lives is
part of the decision, not a detail to settle later.

**This is tooling, and the project has no category for it.** Every story so far belongs to Phase 1, 2
or 3 of `PROJECT_4thBrain.md`, which are product phases, and
`.claude/rules/design-before-implementation.md` requires code to trace to an Epic and a Story. A
generator script is code that traces to neither. The spike should say whether that means a new Epic, a
Phase 0, or an explicit carve-out for tooling. Numbering this P1.21 continues the sequence because the
P1.x series has already become "Phase 1 and everything else structural" — P1.19 and P1.20 are not
skeleton work either — but that is a convention drifting rather than a decision.

**Judge the cost honestly.** This builds nothing a user of 4thBrain will ever see. The case for it is
that the collisions are real, recurring and already documented, that derived data has already drifted
badly once in this repository, and that the volume of agents editing these two files is going up
rather than down — five parallel plans exist precisely so that several changes can run at once, and
they will all want to close a story. The case against is that a generator is a thing to maintain, and
the current cost is annoyance rather than damage. The fidelity check in the acceptance criteria is
where that gets decided on evidence instead of on either of those arguments.

**Timebox: one day.** If Q3 is still open at the halfway mark, take option A (generated regions) and
record that the choice was close, which is how P1.17's brief handled the same risk. Q1 is settled and
should not be reopened inside the timebox.
