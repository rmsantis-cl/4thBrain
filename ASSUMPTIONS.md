# Assumptions — 2026-08-30 batch run

Scope: Story 6.3 (Pipeline Monitoring & Dashboard UI, real), Story 13.3 (Unified Data-Access API, verify-only), Story 1.2 (Unstructured Text Parsing & Sanitization, real). Source plans: `IMPLEMENTATION-PLAN-PHASE-2.md` (root) and `documets/PLAN-30-08-2026-EP1-Completion.md`, reconciled per the task instructions (the newer EP1-completion plan's real design supersedes the older phase-2 plan's mock-first sketch for Story 1.2; Story 13.3's real repository-layer implementation, already committed on `v03`, supersedes the phase-2 plan's original `documentRepository.js`/`tagRepository.js` naming sketch).

## Worktree was behind the "already completed" state described in the task

This run's isolated git worktree branched before Story 13.3's real closeout commits (`67e7d64`, `57cc2e0`, `911703d`, present on `v03` but not reachable from this worktree's branch — confirmed via `git merge-base`). Concretely, this worktree's copies of `server/lib/repositories/document.js` and `job.js` still used an object-destructured constructor signature (`create({ name, uriLocation, ... })`) and referenced `document.parent`/`document.author` columns that don't exist in `documets/design/schema.sql`, while `server/lib/ingest-service.js` and `server/lib/ingestion/ingest-executor.js` (unchanged between this worktree and `v03` — confirmed by diff) already called these repositories with **positional** arguments matching the schema exactly. Every `DocumentRepository`/`JobRepository` call from real application code was broken in this worktree; `server/test/repositories.document.test.js` (also unchanged between branches) already asserted the positional-argument interface and was failing.

`git commit`/merge were off the table per this run's constraints, so rather than re-deriving a fix from scratch (risking a second divergent "fix" for the same bug), I read the already-reviewed correct versions of `document.js`, `job.js`, `documentTag.js` (fixes a genuine unbound-query-param bug — `listForDocument()` called `.all()` with no parameter despite its SQL having a `?` placeholder, so it silently returned every document's tags, not just the requested document's), `tag.js`, and `routes/api/tables.js` (fixes the "document_tag dispatcher leak" — the generic `/:table` dispatcher would 500 on `document_tag`, which has no `list/get/create/update/remove`) via `git show v03:<path>`, and wrote that content into this worktree as plain file edits — not a merge, not a commit. `server/package.json` was brought forward the same way (adds the `chokidar` dependency `server/lib/ingestion/watcher.js` already required but the worktree's `package.json` was missing, and a `test` script; `adm-zip`/`tar`/`cross-env` were the only dependencies dropped, and only after confirming nothing outside the already-dead, unwired `server/lib/job-queue/` tree uses them).

I did not attempt to reconcile every file that differs between this worktree and `v03` — only the ones load-bearing for Story 13.3's own acceptance criteria and for the code Story 1.2 builds on top of. `documets/DESIGN-DEBT.md` and `documets/PLAN-30-08-2026-EP1-Completion.md` were similarly out of date/missing in this worktree; both were written to reflect the same up-to-date content the main checkout already had, plus this run's own additions.

## Story 13.3 — one small, real bug found and fixed beyond the above

`server/lib/repositories/job.js` (both this worktree's original version and the corrected one adopted above) had no `countsByStatus()` method, which the top-level task explicitly required (`SELECT status, COUNT(*) FROM job GROUP BY status`) for Story 6.3's dashboard. Added it, plus a `retry(id)` method (transitions `Failed` → `New`, clearing `start_date`/`end_date`, guarded so it's a no-op unless the job is currently `Failed`) for the dashboard's "Retry" action. Both are small, additive, and covered by new tests in `server/test/repositories.job.test.js`.

## Story 6.3 — no persisted per-job error reason

`documets/design/schema.sql`'s `job` table has no error-message/reason column; `batch/worker.js`'s catch block only logs `err.message` to the structured log stream, never to the row. Story 6.3's "Failed jobs show error reason" (from `IMPLEMENTATION-PLAN-PHASE-2.md`, not stated as literally in `documets/design/Project 4thBrain.md`'s own acceptance criteria) can't be met with real per-job text without a schema change, which is out of this pass's scope (`schema.sql` wasn't touched, and doing so needs its own design decision). Implemented the failed-jobs panel with a fixed, honest placeholder string instead of fabricating detail the system doesn't capture. Logged as Design Debt item 5 in `documets/DESIGN-DEBT.md` rather than worked around silently.

## Story 1.2 — transcoder library and format-handling decisions

Per the task's explicit direction, made the smallest-scope call on each open question from `documets/PLAN-30-08-2026-EP1-Completion.md`:

- **Libraries:** `pdf-parse` for PDF text extraction, `mammoth` (`extractRawText`) for `.docx`. Both are pure-JS with no native binary dependency, matching the rest of this repo's Node-only stack.
- **Images and any other binary format `pdf-parse`/`mammoth` don't cover** (`.doc`, `.zip`, etc.): archive-only. The original is archived to `$VAULT_DIR/raw`; a minimal `.md` stub with YAML frontmatter (`source_raw: <archived path>`, `transcoded_from: <mime type>`) lands in `$VAULT_DIR/incoming` so the item is still discoverable and the transcoded file still "references the archived location of its original raw file" per the acceptance criteria — it just carries no extracted body text. No OCR or vision-model extraction was implemented; that's explicitly out of scope per the task's direction.
- **Malformed/unparseable PDF or `.docx`:** degrades to the same archive-only stub rather than failing the job outright — a corrupt upload shouldn't leave a job permanently `Failed` when the safe fallback (archive the original, note that extraction failed) is available and still satisfies the acceptance criteria's spirit.
- **URL handling:** relocation only, not extraction/scraping, per the task's explicit direction. `server/lib/ingestion/url-relocator.js` is a standalone, tested utility (`relocateToClipping(jobFile, cfg)`) — not registered as a job executor, matching how the plan describes it (only `transcode-executor.js` gets registered in `batch/job-executors.js`). It is **not** wired into `/api/ingest/url`'s live request path: `server/lib/raw-dir-writer.js`'s existing `writeUrl()` already stages new URL submissions directly into `cfg.rawDirClipping`, so that already satisfies the "relocated to `$RAW_DIR/clipping`" acceptance criterion for the one live path that creates URL job_files today. `url-relocator.js` exists for the other arrival path Story 1.1's directory watcher could produce (a URL-shaped file dropped into `$RAW_DIR/inbox` outside the web form) — wiring that path requires a way to recognize "this generic staged file is a URL" that doesn't exist yet, so it's left as a tested-but-unwired utility rather than guessed at.
- **`job_type` selection at ingest time:** `server/lib/ingest-service.js`'s `createIngestJob` now classifies the staged file (reusing `file-validator.classify()`) to choose `job_type: 'ingest'` vs `'convert'`. Without this, `transcode-executor.js` would be unreachable — `batch/worker.js` dispatches strictly by `job.job_type`, and nothing previously created a `'convert'` job. This wasn't spelled out in either source plan but is a necessary, minimal (3-line) connective change for the feature to function at all, not a scope expansion.
- **`batch/worker.js` made `async`:** `pdf-parse`/`mammoth` are Promise-based, so `transcode-executor.js`'s `execute()` had to be `async`. `runCycle`'s dispatch loop was previously a bare synchronous call to `executor.execute()` — changed to `await` it (and `runCycle`/`main` were marked `async` accordingly). `ingest-executor.js`'s existing synchronous executor is unaffected — `await` on a non-Promise value resolves immediately, so this is backward-compatible, not a rewrite of Story 1.1's code.
